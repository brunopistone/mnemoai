# Architecture — Detailed File Map

This is the full per-file reference for the codebase, split out of
`CLAUDE.md` to keep that file lean. See `CLAUDE.md` for the high-level
architecture, key patterns, configuration, and conventions.

> **Not part of the published docs site.** This file is a repo-only
> companion to `CLAUDE.md` — a dense per-file reference meant for AI coding
> agents and contributors working directly in this repository, deliberately
> kept out of `docs/` so it isn't published to GitHub Pages. For the
> human-facing architecture overview, see
> [Architecture](https://brunopistone.github.io/mnemoai/architecture-overview/)
> on the docs site.

**Paths below are relative to the package root `src/mnemoai/`**
(e.g. `client/agent/agent.py` is `src/mnemoai/client/agent/agent.py`).

| `client/agent/agent.py`             | **LangGraph StateGraph agent.** Builds graph with nodes: `classifier`, `decompose`, `orchestrator`, `agent` (call*model), `tools` (execute_tools). ## Key Subsystems — Implementation Detail

Deep implementation notes relocated from `CLAUDE.md` to keep that file
under its size budget. `CLAUDE.md`'s **Key Patterns** section carries the
one-paragraph summary of each; the full behavior, edge cases, and gotchas
live here.

### Config singleton (`utils/config.py`)

All configuration flows through `Config()` which loads `utils/config.yaml` (gitignored). Access via `Config().get("SECTION.KEY", default)`. **Prompts are separate**: every model-facing prompt (`SYSTEM_PROMPT`, `ROUTING_PROMPT`, `ORCHESTRATOR_PROMPT`, `AGGREGATOR_PROMPT`, `SUMMARY_SYSTEM_PROMPT`, `SUMMARY_TASK_PROMPT`) lives in **`prompts.yaml`** (sibling of `config.yaml`, same resolution + seeding; `$MNEMOAI_PROMPTS` overrides), accessed via `Config().prompt("KEY")`. `config.yaml` holds _only_ configuration — prompt keys left there are ignored with a one-time migration warning. There are no hardcoded prompts in the code paths (a bundled package `prompts.yaml` provides the defaults; tiny computed crash-guards exist only for a totally-missing file). `_load_prompts` **layers the bundled package `prompts.yaml` underneath the user's file** (user keys win, missing keys fall back to the bundle) — so a NEW prompt shipped in a release resolves on an EXISTING install whose seeded `prompts.yaml` is never overwritten, while user customizations still take precedence. The `.system_prompt` property reads `SYSTEM_PROMPT` from prompts.yaml.

### Server-side safety policies (`server/tools/safety/`)

Two pure classifiers enforce, **inside the MCP server**, the hard limits the tool docstrings advertise — a floor that holds even if the server subprocess is driven directly (not via the client's `_confirm_tool` gate). Deliberately narrow: they block only **catastrophic, irreversible** actions, NOT ordinary scoped mutations (those stay gated by the client confirmation + plan mode). `bash_policy.classify_shell_command(cmd) -> BashPolicyResult` blocks root/home recursive force-deletes (`rm -rf /|~|/*`), `mkfs*`, raw-device `dd`/`shred`/`wipefs`, power-state changes (`shutdown`/`reboot`/`halt`/`poweroff`, `init 0/6`), and the fork bomb — enforced at the top of `execute_bash` **and** `start_background_task` (one shared policy, so shell safety isn't duplicated). `path_policy.classify_write_path(path) -> PathPolicyResult` normalizes `..`/`~` then blocks writes into system dirs (`/`, `/etc`, `/bin`, `/usr`, `/boot`, `/dev`, `/System`, `/Library`, …; NOT the macOS `/private/var/folders` temp dir) — enforced in `fs_write` and `file_edit`. Both are config-independent and unit-tested (`tests/unit/test_safety_policies.py`). This is the server-side complement to the client-side `_confirm_tool` gate and plan mode.

### Blocking tools off the event loop (`server/tools/thread_offload.py`)

The MCP server is ONE stdio subprocess with ONE event loop, and the SDK dispatches every incoming request concurrently (`tg.start_soon(self._handle_message, …)` in `mcp.server.lowlevel.server`) — so parallel agents (orchestrator waves, `spawn_agent` sub-agents) genuinely have several tool calls in flight at once. A tool body that does synchronous work never yields, so while it runs that single loop cannot dispatch another call, read a new request, or even write back a response it has already finished: **one blocking tool freezes the whole tool layer for every agent**. Declaring the tool `async def` does not help — it's the body that matters, and FastMCP runs a plain `def` inline too (`func_metadata.call_fn_with_arg_validation` → `return fn(**arguments)`, no thread offload). The bug this fixed: 24 of the 31 tools were `async def` with no `await` anywhere, so with three orchestrator workers and two `explore` sub-agents calling tools, one `execute_bash` starved every other in-flight call until the client's `LLM.MCP_CALL_TIMEOUT` (300s) killed it — a `glob_search` or `memory` call whose real work is milliseconds timed out at 300s, and the user had to cancel by hand. Worst case was a wait the client explicitly supports: `wait_for_task(timeout_seconds=1500)` polls with `time.sleep(1)`, and `mcp_tool_wrapper._call_deadline` raises only the CALLING agent's deadline, so every parallel agent kept the 300s default and was mathematically guaranteed to fail.

**The convention, and both halves are load-bearing: a tool is `async def` only if it really awaits.** Everything else is a plain `def`, wrapped by `offload_blocking` and run via `anyio.to_thread.run_sync` (anyio, not `asyncio.to_thread` — the SDK server runs on anyio, so this uses its capacity limiter). `ThreadedToolServer` applies it at the single registration chokepoint (`ToolManager.register_tools` reassigns `mcp` to the proxy) rather than per tool, so a tool added later is covered by construction; it's a proxy, not a subclass or monkeypatch, so it assumes nothing about FastMCP internals beyond `tool()` returning a decorator and an SDK upgrade can't silently disarm it. `tool()` registers the wrapper but hands the ORIGINAL function back, keeping the name inside each `register_*` bound to the real implementation (what the unit tests capture and call directly). `functools.wraps` is what keeps the MCP contract identical and must NOT be paired with an explicit `__signature__`: FastMCP builds the input schema with `inspect.signature(fn, eval_str=True)`, which follows `__wrapped__` to the original and evaluates its annotations in the ORIGINAL module's globals — setting `__signature__` stops that unwrapping and resolves them against `thread_offload` instead. `iscoroutinefunction` does not follow `__wrapped__`, so the SDK still sees an async callable and awaits it. Consequently `tool_error_handler` is polymorphic (sync in → sync out, async in → async out) over one shared except-chain (`_error_response`), since an async-only wrapper would force every blocking tool back to `async def`.

Two tools legitimately stay on the loop because they really await: `web_search` (aiohttp) and `web_crawler` (crawl4ai — its one blocking call, the ~260MB one-time Playwright Chromium download, is offloaded explicitly). Enabling real concurrency also made the tools' shared state genuinely concurrent, which is safe because it already used atomic writes (`atomic_write_json`/`atomic_write_text`), `background_tasks._task_lock`, and GIL-atomic dict operations in `read_state`.

**`fs_read` was the hole the first pass left, and it is why the guard now covers HELPERS too.** It was `async def` and awaited its readers, so it satisfied a check that only looked at decorated tools — but every reader was itself an await-free `async def` (and `chunking_helper.__summarize_with_model` did a blocking `model.invoke`), so the entire chain ran inline on the loop. **An `await` on a coroutine that never suspends buys nothing; only the leaf matters.** Worse, `read_lines` re-counted `count_tokens(full_content + line)` on every line — quadratic in tokenizer work, measured at **9.8s for one 2839-line source file against 0.007s for a single count of the same text**, and with `DOC_MAX_TOKENS` sized for a large-context model the loop runs to EOF, so one `fs_read` of a big file burned tens of seconds to minutes of CPU **on the event loop**. That is the reported failure: a parallel reviewer sub-agent reading files while another agent's `glob_search` — milliseconds of real work — died at the client's 300s `MCP_CALL_TIMEOUT`. `fs_read` and every reader are now plain `def` (offloaded at the chokepoint like any other blocking tool), the token accounting in `read_lines`/`read_json` is incremental (a running total plus the new line, which sums slightly HIGH — the safe direction for a limit — with one exact count of the final content for the payload), and `process_large_content` fans its chunks out over a `ThreadPoolExecutor` bounded by `CHUNKING_CONCURRENCY` (the old asyncio semaphore never yielded, so the chunks were serial AND on the loop). Its progress lines go to the logger, never `print`: stdout in the server subprocess IS the JSON-RPC pipe.

`tests/unit/test_thread_offload.py` pins every half: the offload's behavior + unchanged `Tool.from_function` schema, an order-based pair showing starvation vs. concurrency, and **two AST scans over `server/tools/`** (parsed, not imported, so they cover the config-gated groups a unit run never registers) — one over `@mcp.tool()`-decorated functions, one over **every** `async def` in the package, each failing on a body with no `await`/`async with`/`async for`. The second has a detector self-test so it can't pass because the scan broke rather than because the code is clean.

### External MCP servers (`client/mcp_config.py`, `MultiMCPClient`)

The built-in server is always launched; additional stdio MCP servers can be declared in `~/.mnemoai/mcp/mcp.json` (standard `mcpServers` schema; legacy flat `~/.mnemoai/mcp.json` still read). `load_external_servers()` parses them (tolerant: missing/bad file or entry → skip, don't crash). `MultiMCPClient` (in `mcp_tool_wrapper.py`) owns the built-in wrapper + one per external server, connects them together, and merges tools — namespacing a colliding external tool as `servername__tool` (built-in names always win; the server is still called with the original name). External tools are appended to **every** route in `agent.py` — including the no-tools `simple_qa` route — so routing never hides them (a short factual question like "what time is it?" classifies as `simple_qa`, so an external server such as `time` must be reachable there too). When orchestration is enabled, `_external_tools_prompt_block()` injects the external tool names/descriptions into the decomposition prompt and instructs the decomposer to route subtasks needing them to the `full` category (which binds every tool) — otherwise the decomposer, unaware they exist, can't target them. `/mcp` lists status.

### Multi-provider LLM abstraction (`models/controllers/llm_controller.py`)

`LangChainLLMController.initialize_model()` dispatches on `MODEL_ID.TYPE` (bedrock/mantle/ollama/openai/anthropic/sagemaker/litellm/mlx). Each provider's supported config keys / client-kwarg mapping live in `models/provider_params.py` (consumed via `build_kwargs`). For anything the registry doesn't model, every section accepts an `EXTRA_PARAMS` dict — a generic passthrough merged verbatim into the model's request body (`provider_params.extra_params`), used e.g. for `reasoning_effort` (OpenAI/Mantle responses) or `thinking` (Anthropic/Mantle anthropic). Note: `anthropic` is the direct Anthropic API (`ChatAnthropic`, `ANTHROPIC_API_KEY`), distinct from Mantle's `anthropic` _protocol_ (Claude via Bedrock).

### Bedrock Mantle (`models/mantle_factory.py`)

`TYPE: mantle` reaches AWS Bedrock Mantle via a bearer token minted from standard AWS (SigV4) credentials. `API_PROTOCOL` selects the wire protocol: `chat_completions` (OpenAI `/v1`), `responses` (OpenAI Responses `/openai/v1`, e.g. GPT-5.4), `anthropic` (Anthropic Messages `/anthropic`, Claude). The factory is shared by the LLM and vision controllers. Model availability varies by region (e.g. GPT-5.4 is in us-west-2).

### Prompt caching (`models/prompt_cache.py`)

One turn is many model calls over a prompt that only grows (system prompt + tool definitions + steering + every prior message and tool result), so the stable prefix is marked with a cache breakpoint: later calls read it at a fraction of the input price and the provider skips prefill it already did — the part that dominates time-to-first-byte (see the ~123s measurement in `llm_controller._boto_config`).

**One kwarg, two expansions.** `bind(model, policy)` attaches a single `cache_control` kwarg. `langchain-aws` expands it into Converse `{"cachePoint": {"type": "default"}}` blocks (after the system blocks, after `toolConfig.tools`, and after the last message; it reads only `ttl`); `langchain-anthropic` forwards it as the Messages-API top-level `cache_control` marking the last cacheable block (`ttl` ∈ `5m`/`1h`, requires `type: "ephemeral"`). One dict — `{"type": "ephemeral", "ttl": "5m"}` — satisfies both.

**The system prompt is marked too, but ONLY on the Anthropic-shaped transports** (`policy(...).mark_system`, applied by `agent._system_message`). The per-turn injections (`<steering>`, the episodic block, the plan reminder) ride the newest user message and are stripped before storage, so the END of one request is never a prefix of the next and a tail-only marker matches nothing on the following turn; a marker on the system block is immune to that. Measured on the same request: **0 cached tokens read with the tail marker alone, the whole 4812-token system prefix read once the system block was marked.** Bedrock places its own breakpoint after the system blocks and would reject an Anthropic-style key inside a Converse block, so it doesn't get the extra marker.

**Provider gating is mandatory, not conservatism:** `ChatOpenAI` would send the unknown kwarg and get a 400, and Bedrock rejects a `cachePoint` for a non-caching model family. Hence `CACHEABLE_TYPES` × `_CACHEABLE_FAMILIES`, with `mantle` additionally requiring `API_PROTOCOL: anthropic`. There is deliberately **no client-side size gate**: a prompt under the provider's minimum (~1024 tokens) is silently not cached, which costs nothing.

**Two wiring invariants.** (1) Everything flows through the agent's two chokepoints — `_bind_tools` (every route model, `rebind_model`, the orchestrator worker, and `subagent_runner`'s sub-model) and `_system_message` (`_run_worker_loop`, `_call_model`, `_compact_and_rebuild`, `invoke`) — so a new call site can't silently skip caching; both are source-guarded by `test_prompt_cache.py`. (2) The cache bind lands only AFTER `bind_tools`, never on `agent.model` itself, because `subagent_runner.callback_free_model` calls `model_copy(update={"callbacks": None})`, which a `RunnableBinding` doesn't have. `rebind_model` re-reads the policy first, so `/params` (which reloads in place) really does apply a `PROMPT_CACHE` change. `usage_metadata.input_tokens` still INCLUDES cache reads, so `_capture_input_tokens` and the compaction high-water trigger keep their meaning.

### Conversation compaction (`client/managers/agent_conversation_manager.py`)

Keeps the conversation under `MAX_CONVERSATION_TOKENS` by summarizing older messages into the system prompt while keeping recent turns verbatim. Triggers automatically when over budget, or manually via `/compact`. The kept window is bounded by message count AND a token budget so an oversized recent message (e.g. a pasted document) is summarized, not kept. Tool calls/results are preserved in the summary. The summary uses a structured prompt (a "summarizing conversations" system framing + a 9-section `<analysis>`-then-summary task template, with `/compact <focus>` injected as compact instructions); the `<analysis>` scratchpad is stripped, and the injected block carries a continuation instruction so the model resumes seamlessly. **The split point is tool-pair-safe** (`_safe_tool_boundary`): it never starts the kept window with an orphaned tool result nor cuts an assistant tool-call turn from its results — which would otherwise make the OpenAI Responses API reject the next turn with "No tool call found for function call output".

**Context-overflow protection (layered, prevents the runaway 400-loop). Size knobs auto-derive from `MAX_CONVERSATION_TOKENS` (the model's context window) so they scale per-model, not a fixed number:** (1) **Cap tool results at the source** — `tool_formatting.truncate_tool_result` bounds each `ToolMessage` to `LLM.MAX_TOOL_RESULT_CHARS` (defaults to 10% of the window in chars, ~4 chars/token; head+tail kept with a truncation note; 0 disables) at both tool-exec chokepoints (`_execute_tools`, `_run_worker_loop`), so one runaway result (e.g. `grep_search(max_results=4000)`) can't alone overflow the window. (2) **Pre-flight compaction, layered** — `client._compact_now` (wired into the agent as `_compact_provider`, called at the top of `invoke()`) proactively compacts when history exceeds `LLM.COMPACT_HIGH_WATER_TOKENS` (defaults to 80% of `MAX_CONVERSATION_TOKENS`, 0 disables), the "count before send" analog. **The over-budget test prefers the provider's exact `input_tokens` (`agent._last_input_tokens`, the ground truth shown as `[Context: N]`) when a turn has run, falling back to the estimate only before the first call** — the estimate (tiktoken over the serialized message JSON × a per-provider safety multiplier, e.g. 1.5× for anthropic/mantle) over-counts the real prompt ~2× and would fire compaction far too early. It tries the **cheapest layer first**: `AgentConversationManager.evict_old_tool_results` shrinks the bodies of _old_ tool results (outside `LLM.TOOL_EVICTION_KEEP_RECENT`, default 8) to a short head + a marker (`LLM.EVICTED_TOOL_RESULT_CHARS`, default 500; 0 disables), with **no model call** and **without dropping any message** (only content is trimmed, so tool-call/result pairing is preserved); if that alone gets back under the high-water mark the expensive full summary is skipped — and `client._log_eviction_checkpoint` records the now-smaller history as a session checkpoint, since `_compact` (which writes its own) never ran and the transcript still holds each result at full size. Otherwise it falls through to `_compact`. **`_compact` runs `evict_old_tool_results` FIRST on every path** (manual `/compact`, post-turn auto, and the overflow backstop — not just the proactive check), then summarizes what remains. **The summary is a parallel map + single reduce** (`generate_summary`): each batch is summarized concurrently (bounded by `LLM.SUBAGENT_MAX_CONCURRENCY`), then one reduce call (`_reduce_summaries`) folds the ordered partials + any prior compaction summary into a coherent whole (a single batch with no prior summary skips the reduce) — wall-clock is ~one batch + one reduce, not the sum of all batches. The summary runs on a **reasoning-disabled variant of the same model** (`llm_controller.build_non_reasoning_model` — clears `REASONING`/`REASONING_EFFORT`, and `verbose` for Ollama; provider-agnostic no-op where thinking doesn't exist; `LLM.SUMMARIZATION_THINK: true` keeps thinking on), since a slow extended-thinking pass is the dominant compaction cost and adds nothing to a summary. (3) **Overflow backstop** — `_is_context_overflow_error` classifies a "prompt is too long"/context-window 400 in `_stream_once`; instead of re-invoking the same oversized prompt (the old loop), it force-compacts for the next turn and returns a terminal AIMessage so the turn ends. All are guarded with `getattr(self, "_compact_provider", None)` so bare test objects still work.

**A compaction that happens DURING a turn has to be carried into the rest of that turn — the graph state can only grow.** `AgentState.messages` is `Annotated[Sequence[BaseMessage], operator.add]`, an append-only channel: a node cannot shrink it, and `invoke()` seeds it from `self._messages` ONCE, so the two lists diverge the moment compaction replaces `agent.messages`. The overflow backstop rebuilt only the immediate retry prompt (`_compact_and_rebuild`), which meant the retry succeeded and then the NEXT model call — the one after the tool the model just ran — re-read the untouched state and re-sent the same oversized prompt. The second overflow arrives with nothing left to compact, so the turn dead-ends on the terminal "couldn't compact it further" **over a history that was just reduced to two messages**: observed live as `prompt is too long: 3155357 tokens > 1000000` (compacted and retrying) followed 2435 tokens later by the same error (could not compact), the +2435 being only the two tool results in between. Three pieces close it: `invoke()` records **`_turn_seed_len = len(initial_state["messages"])`** (the boundary between seeded history and what this turn produces) and clears the stash so a previous turn's compaction can't leak in; the backstop stashes `_mid_turn_compaction = (rebuilt, seed)`; and **`_apply_mid_turn_compaction(messages)`** — a no-op until something is stashed — returns `compacted + messages[seed:]` at the top of every `_call_model`. Two ordering requirements: it runs on the **RAW** state list, before `_sanitize_tool_pairs` (which can DROP messages and shift the index), and the retry prompt itself is rebuilt through the same substitution so the tool calls and results already produced this turn ride along — otherwise the model silently redoes work it had finished. The seed index is the same idiom `_run_worker_loop` already uses (`worker_messages[_seed_len:]`), applied to the graph channel.

**`_commit_turn` commits only what the turn PRODUCED — the mirror of the same problem.** It used to append every message in the final state that was not already in `self._messages`; that dedup silently stops working after a mid-turn compaction, because the summarized-away messages are no longer in that list. So the turn ENDED by appending all of them back — undoing the compaction it had just performed — and `_log_turn` wrote them to the append-only transcript as this turn's work, inflating the file too. The next turn then re-summarized the same history: live signature `Compacted: summarized 1209 older messages, kept 2 recent` followed one turn later by `Summarizing 1165 older messages`, the difference being exactly the 44 `HumanMessage`s the commit filter drops. Slicing the state at `_turn_seed_len` (via `getattr`, so `__new__` test stubs still work) makes "what this turn produced" structural instead of inferred.

**A cached provider token count must not outlive the history it measured** (`client._forget_context_size`). The pre-flight check prefers `agent._last_input_tokens` (ground truth) over the estimate, and `_compact` already nulls it — but so must every path that REPLACES live history: `resume_session`, `load_conversation`, `branch_conversation`. The transcript those paths rehydrate is append-only and never compacted, so it restores everything compaction had summarized away: the count left over from the compacted state describes a much SMALLER conversation than the one now in memory. The high-water test therefore passed on a 3.15M-token history and the first turn after a `/branch` went straight to a provider-side overflow — the layer designed to prevent exactly that was skipped because its input was stale. A unit test source-guards all three call sites, since the failure is invisible until a real turn runs.

**Output-token truncation → auto-continue (not a dead-end).** Distinct from the _input_ overflow above: when the model's OUTPUT hits `MODEL_ID.MAX_TOKENS` mid-turn (common with `REASONING_EFFORT: max` on a large context — reasoning + a partial answer/tool call exhaust the budget), the turn finishes with `stop_reason: max_tokens` and no completed tool call. `_call_model` detects this (`_was_truncated_by_tokens`) and **auto-continues** via `_continue_truncated_turn`: it feeds the partial turn back with a "continue where you left off" nudge and re-streams, accumulating visible text, up to `LLM.MAX_OUTPUT_CONTINUE_RETRIES` (default 3). Parts are glued directly (each is `_extract_visible`-stripped, so a resumed stream can't gain a spurious space mid-word). It stops early when a continuation finishes cleanly (returns the assembled answer) or emits a tool call (returned so the graph runs it, partial text preserved). Only if retries exhaust with nothing usable does it surface the "increase MAX_TOKENS" message — otherwise the user never has to type "continue". This replaced the earlier dead-end that ended the turn with a warning.

**Stalled-stream recovery (dead socket / laptop sleep).** A streaming read (`model.stream()`) is a blocking C-level socket read; if the connection dies silently mid-response (the laptop sleeps and the TCP socket dies), it would park the single worker thread forever — the turn looks stopped AND new input freezes behind it (FIFO worker). The provider's own request timeout only covers getting response HEADERS, not a stalled body, so it can't help. mnemoai consumes the stream through a per-chunk idle-timeout watchdog: `_iter_stream_with_idle_timeout` runs `model.stream()` on a daemon reader thread feeding a `queue.Queue` and times each `get(timeout=LLM.STREAM_IDLE_TIMEOUT)` (default 120s; 0 disables → iterate directly). **The wait for the FIRST chunk gets its own, longer budget** (`_stream_first_token_timeout`, from `stream_policy.first_token_timeout` = `LLM.REQUEST_TIMEOUT` + a 30s grace, never below the idle window): that wait is the provider prefilling and reasoning over the whole prompt, not a stalled socket, and on a large context it legitimately outlasts the per-chunk budget (~123s measured at ~440k tokens). Policing it with the per-chunk window aborted healthy turns on a big conversation, and since each retry re-sent the same prompt and re-paid the same doomed prefill, the turn could never complete — botocore's 60s `read_timeout` trap, one layer up. Once real data flows the window narrows back to `STREAM_IDLE_TIMEOUT`, so a socket that dies mid-response is still caught fast; the message says which window tripped (`No first token for Ns` vs `No stream data for Ns`). **A contentless chunk does not count as data** (`stream_policy.chunk_has_payload`): an OpenAI-shaped server (local MLX/llama-server/vLLM) emits a role-only `delta` the instant it ACCEPTS the request, before prefill starts, and narrowing on it undid the whole widened window — measured on MLX, the priming chunk at +0.01s and the first real token at +300s on a 43k-token prompt, so a healthy server timed out at 120s and each retry re-paid the prefill. The budget is a wall-clock deadline rather than a per-empty-poll accumulator (a server emitting keep-alives faster than `_CANCEL_POLL_SECONDS` would otherwise never let it expire) and is re-armed AFTER the `yield` returns, so it measures the wait for the next chunk and not the consumer's render time. No chunk within the window → raise `_StreamIdleTimeout` and ABANDON the reader (a daemon; can't force-kill a C socket read, so it unwinds when its socket finally errors). `_stream_response` then treats `_StreamIdleTimeout` + transient network errors (`_is_transient_network_error` — reset/broken-pipe/timeout/5xx/overload, provider-agnostic substrings; **botocore spells the same failures out in prose**, so its wordings are matched explicitly — only `ReadTimeoutError`/`ConnectTimeoutError` contained an existing marker, leaving five of its seven transport errors classified as deterministic and retried zero times, `ConnectionClosedError` among them: it says "Connection **was** closed …", which `connection closed` does not substring-match, and that is exactly how a dropped Bedrock `converse-stream` socket surfaces) as retryable and re-runs the turn on a fresh connection with exponential backoff (reusing `LLM.RETRY_DELAY`/`RETRY_BACKOFF`, capped 30s), discarding the partial (a dropped stream can't resume mid-generation). Exhausted retries surface a terminal "lost the connection — send your message again" AIMessage (never a crash). `_ContextOverflow` is excluded from this retry (the caller compacts instead). Lives in the stream layer, so it's provider-agnostic.

**The auxiliary calls retry the same failures (provider overload / 529).** An overloaded provider rejects every call in flight at once, so the three NON-streamed calls a turn makes — route classification (`router._classify_with`), task decomposition (`agent._decompose_task`), and the compaction summary map/reduce (`agent_conversation_manager.generate_summary`) — get the same 529 the streamed turn does. Each has a graceful fallback (bind every tool / one `full` subtask / drop that batch), and that is precisely why they had **no retry at all**: nothing crashed, so the turn silently lost its routing and its decomposition while the stream beside it recovered on attempt 2, and the only trace was a `Router classification failed` line. `stream_policy.call_with_transient_retry` (sync, for `invoke`) and `acall_with_transient_retry` (async, for the summary's `ainvoke`) drive them: retry only `is_transient_network_error`, re-raise anything deterministic immediately, and re-raise the LAST transient too so the existing fallback still runs. Attempts are capped at `AUX_RETRY_ATTEMPTS` (3) even when `LLM.MAX_RETRIES` is higher (`aux_attempts`) — a working fallback makes a quick second chance better than a long stall, the opposite trade-off from the streamed turn, where giving up costs the user the whole answer. Per-attempt waits log at DEBUG through one shared wording (`retry_notice`, so the pure module needs no logger); the sync driver waits on the agent's cancel event, the async one has none because an async caller is cancelled through `CancelledError` (a BaseException the `except Exception` deliberately lets through). The compaction map is the site that mattered most: it fans every batch out concurrently, and a dropped batch means that slice of history is gone from the summary for good.

**Backoff is jittered and defers to the provider.** `network_retry_delay(attempt, base, factor, jitter=…)` adds up to `RETRY_JITTER` (25%) of the delay at random, applied AFTER the 30s cap — a capped delay is still a collision point, and orchestrator waves, spawned sub-agents and the compaction map all fan out together, so a deterministic backoff had every one of them come back at the same instant and re-collide. Jitter defaults to 0 in the pure function (callers opt in) so the math stays reproducible. `retry_after_seconds` reads the provider's own `retry-after` from either shape the supported stacks produce — an httpx/requests response object with a header mapping (Anthropic/OpenAI SDKs) or botocore's response dict — and takes it over our guess when present (capped at 60s); a non-numeric or HTTP-date value is ignored rather than guessed across a clock skew. `transient_retry_delay` combines the two and is what both drivers and `agent._transient_retry_delay` (the streamed turn) use.

### Orchestrator-workers (`client/agent/orchestrator.py`, `client/agent/agent.py`)

For "full" complexity tasks: decompose → parse subtasks (JSON) → run worker loop per subtask with category-specific tools → aggregate results. **Decomposition is its own graph node (`decompose`), and the agent-vs-orchestrator route is chosen on the ACTUAL subtask count.** The classifier sends a non-trivial `full` task to `decompose` (`_route_after_classify` → `"decompose"`); `decompose` (`_decompose`) runs `_decompose_task` and stashes the result in the `subtasks` state channel (a plain LastValue channel — NOT `operator.add` — written once, no `messages` key so a fallback keeps history pristine); `_route_after_decompose` then sends ≥2 subtasks to the `orchestrator` and ≤1 (atomic task, or none) to the normal streaming `agent` — so the old degenerate "Step 1/1" quiet worker is gone; an atomic task streams with the full toolset and native history. Trivial and plan-execution turns skip `decompose` entirely (no extra LLM call). `_orchestrate` reuses the pre-decomposed `subtasks` from state, but **decomposes internally if the channel is unset** (direct callers / tests), so it stays backward-compatible; it keeps the `len(subtasks) == 1` no-aggregator branch for those direct callers. **The decomposer AND every worker receive the REAL prior conversation** (`_prior_history(state["messages"])` → drops the leading system prompt(s) + the trailing current-query HumanMessage, then `_sanitize_tool_pairs`), inserted between their own system prompt and the current subtask — so a context-dependent follow-up ("write the issue to a file", "fix it") resolves its references against the same conversation the main agent sees, instead of the worker fabricating content. It's **uncapped** (`state["messages"]` is already bounded to the window by compaction; an extra cap would be redundant and could drop the referenced turn) and threaded ONLY along this path via a `history` param on `_decompose_task`/`_run_subtasks_scheduled`/`_run_subtask`/`_run_worker_loop` — the injected messages sit before a `_seed_len` marker so they're excluded from the saved `worker_msgs` (no per-worker duplication). `spawn_agent`/`resume_agent` sub-agents pass no `history` (default None), preserving their deliberate context isolation. **Subtasks are scheduled by a `depends_on` graph, not strictly sequentially:** `parse_subtasks` reads an optional `depends_on` (0-based indices of earlier subtasks; sanitized to a DAG — self/forward/out-of-range/non-int refs dropped), and `_run_subtasks_scheduled` runs each **wave** of dependency-satisfied subtasks **concurrently** on the same bounded `ThreadPoolExecutor` the parallel sub-agents use (`LLM.SUBAGENT_MAX_CONCURRENCY`; a lone/last wave runs inline), threading only a subtask's _declared_ dependency results into its prompt (`_run_subtask`, workers run `quiet=True`). Independent subtasks run in parallel; a chain runs in order; a broken/cyclic graph can't deadlock (an empty ready-wave force-runs the remainder). Backward-compatible: no `depends_on` → sequential, with all prior results as context (the pre-existing behavior). **Parallel-wave workers run HEADLESS** (thread-local `_headless_tl` set around each pool worker): several run at once, so an untrusted destructive tool auto-DENIES rather than stacking interactive confirm prompts on one terminal (a category already in `_trusted_confirm_categories` still proceeds) — the same safety rule as background sub-agents. A lone/sequential wave (`SUBAGENT_MAX_CONCURRENCY=1`) runs inline and CAN prompt.

### Sub-agents (`spawn_agent`) (`client/agent/subagents.py`, `server/tools/subagent_tool.py`)

Model-initiated sub-agents, distinct from the framework-driven orchestrator: the model calls `spawn_agent(agent_type, prompt, description)` to hand a self-contained task to a fresh sub-agent that runs on its **own isolated context** and returns **only its final report** — the sub-agent's intermediate tool calls never enter the parent's window (the whole point: context isolation for search-/multi-step-heavy work). Same thin-stub + client-side-interception split as `exit_plan_mode`: `subagent_tool.py` is a stub, `agent._handle_spawn_agent` supplies the real behavior at both tool chokepoints (`_execute_tools`, `_run_worker_loop`), and `spawn_agent` is in `_ALWAYS_AVAILABLE_TOOLS`. It reuses `_run_worker_loop` (which already runs on an isolated `worker_messages` list) in **`quiet=True`** mode — which **still streams** the model call (`_stream_once_quiet`, so it keeps the stalled-stream idle-timeout + network retry: a sub-agent whose socket dies on sleep must not hang) but **suppresses all display** and touches no shared display state (no reasoning/tool markers, no `print`, no shared `_code_formatter`/spinner) — i.e. it streams under the hood and merely drops the delta events (display suppression), NOT a non-streaming call. So the sub-agent's trace stays out of the terminal (**display** isolation, complementing context isolation) and it's safe to run several concurrently; a `progress` callback drives a live "N tool calls…" spinner label instead of the trace. It selects the type's tool subset via `_subagent_tools` (allowlist + always-added meta tools, `spawn_agent` always removed → no nested spawning; also guarded by `_spawn_depth`, which is **thread-local** so parallel top-level spawns don't share a counter). **Concurrency:** when the model emits several `spawn_agent` calls in one turn, `_run_spawn_batch` runs them on a bounded `ThreadPoolExecutor` (`LLM.SUBAGENT_MAX_CONCURRENCY`, default 4; 1 = sequential; a lone spawn runs inline) and keys results by `tool_call_id`; a failing sub-agent yields an error string, never aborting siblings. Concurrent `_confirm_tool` prompts are serialized by `_confirm_lock` (with a re-check of trusted categories inside the lock). Types live in `subagents.py` (built-in: `general-purpose` = full tools, `explore`/`plan` = read-only), each with a `prompts.yaml` system prompt (`SUBAGENT_{GENERAL,EXPLORE,PLAN}_PROMPT`, via the bundled-fallback loader so they reach existing installs; in-code crash-guard fallbacks in `subagents.py`). **Custom types** are authored as `~/.mnemoai/agents/*.md` (frontmatter `description` required, optional `name`/`tools` [list or CSV; `*`/omitted = all]/`disallowed-tools` [a denylist applied after the allowlist; `*`/`all` = deny everything]/`model` [a per-agent same-provider model NAME override, built by the client factory with only `MODEL_ID.NAME` swapped], body = system prompt) via `_load_custom_subagents` — a tolerant scan (bad file reported+skipped, mirroring `SkillStore`/`load_external_servers`) using the shared `_parse_frontmatter`; a custom type overrides a built-in of the same name (`list_subagents` merges built-ins ∪ custom, custom wins). There's **no `/agents` command** (agents are files, the model decides when to spawn): discoverability comes from `available_subagents_block()` (single source in `subagents.py`), injected as an `<available_subagents>` block by `client._inject_subagents_context` at session start and re-injected by `AgentConversationManager._subagents_block` after compaction (same survive-a-summary pattern as `<available_skills>`). **Background + resume:** `run_in_background` **defaults to true** — most delegations run detached so the main turn stays responsive; the model passes `false` only when it needs the report to continue the turn (its next step depends on it) or a `general-purpose` sub-agent must edit/run un-approved things (a background one runs headless and would auto-skip them). `_run_spawn_batch` only batches the explicit-`false` (foreground) spawns; background ones launch via the inline path. `spawn_agent(…, run_in_background=true)` runs on a daemon thread via `_launch_background_subagent` and returns immediately with an id; the run is tracked in `_bg_agents` (a `BackgroundAgentRegistry` in `client/agent/background_agents.py` — thread-safe state + a per-run `subagent_<id>.json` record under `tasks_dir()`, swept at startup by `sweep_old_task_logs` on the same 7-day policy as background bash `*.log` files so it can't grow unbounded). On completion the daemon fires `_on_background_complete(agent_id)` (a UI hook: `reader.notify_background_complete`) which, **when the session is idle**, enqueues an empty line → a **delivery-only turn** that auto-surfaces the report without the user typing; if a turn is running it no-ops and the completion is drained at the start of the next turn instead. Completions are drained at the top of `invoke()` (`drain_background_completions` → wrapped `HumanMessage`s appended to history); a delivery-only `invoke("")` runs on those messages alone (no empty user turn), and `client.query("")` skips the per-turn injections for it. `resume_agent(agent_id, prompt, run_in_background=True)` (`_handle_resume_agent`, also in `_ALWAYS_AVAILABLE_TOOLS`, intercepted at **both** chokepoints) re-runs a finished type with its original task + prior report + the follow-up. It **defaults to background** (via `_launch_background_subagent`, matching the original background run) so resuming a background agent stays background; `run_in_background=False` runs it foreground/inline. On a registry miss it falls back to the persisted JSON record (`load_from_disk`), so a finished sub-agent stays resumable **across a restart / loaded conversation** (the in-memory registry doesn't survive, but the per-run record does — it persists the original `prompt` for this). **Confirmation:** foreground sub-agents run through the same `_confirm_tool` gate as the parent (they CAN prompt); a **background** sub-agent runs headless (thread-local `_headless_tl`, set on its daemon thread), so `_confirm_tool` auto-**DENIES** an untrusted destructive tool (never auto-allows) — it proceeds only via a category already in `_trusted_confirm_categories`. All four phases (sequential/fresh, custom types, bounded concurrency & quiet display, background+resume) shipped. **Live visibility + control:** every hidden run (foreground batch, background, AND orchestrator subtask worker) also opens a run in `AgentActivityStore` (`client/agent/agent_activity.py` — thread-safe, bounded ring buffer, per-run cancel `Event` shared with snapshot copies), threaded through `_run_worker_loop` as an `activity` sink that records each tool call / result / error / final answer (this also tags an otherwise-anonymous worker tool error to the specific agent). The pinned TUI reads snapshots to draw the bottom **agents panel** (Ctrl+A nav-mode: ↑/↓ select, Enter opens a full-screen detail view via `run_dialog` rendered through `turn_view.render_agent_detail`, Esc exits) and to **stop** agents: `x` requests a per-run stop (`store.request_stop`), `Ctrl+X Ctrl+K` stops all + cancels the turn; the worker loop polls `activity.is_cancelled()` (and the global `_cancel_event`) each iteration and `_should_continue` ends the graph on cancel, so a stopped agent — foreground or background — actually halts. A stopping run shows an animated `cancelling…` label until it flips to `stopped`. The panel is a **scrolling viewport** (`_PANEL_MAX_ROWS` rows) over EVERY run the store retains, not the tail of the list: `_agent_rows()` returns all of them, the nav cursor is held in full-list coordinates and `_panel_window()` slides the viewport to follow it, so any run can be selected, viewed or stopped. Idle (non-nav) the viewport stays anchored to the NEWEST rows — jumping to an old row whenever one kept running would hide the fresh activity a glance is for — and the hint line instead reports what's cut off (`+N more (K running)`), with Ctrl+A landing the cursor straight on the oldest still-running agent. Ctrl+A is gated on "any run exists" (`_agents_navigable`), NOT on the panel being visible, so a finished agent's report stays reachable after the panel auto-hides. Rendering only the tail (`rows[-6:]`) made everything older unselectable — in an 11-agent fan-out a still-running early agent was invisible with no way to reach it — so the retention bound belongs to the store (`MAX_RUNS`, which never evicts a running run), never to the renderer.

### Agent collaborators (`client/agent/{message_codec,message_sanitizer,plan_policy,tool_formatting,confirmation_gate,tool_loop}.py`)

`LangGraphAgent` is the coordinator; its **stateless** logic lives in sibling modules so the class stays focused on the graph/loop. `message_codec` = Strands↔LangChain message conversion; `message_sanitizer` = orphaned tool-pair repair (`sanitize_tool_pairs`); `plan_policy` = the plan-mode block decision + read-only-bash heuristic + data tables (`PLAN_BLOCKED_TOOLS`, `READONLY_BASH_CMDS`, …); `tool_formatting` = the `[⚙ …]` marker rendering (`format_tool_call`/`elide_middle`), `normalize_tool_args`, and `tool_error_message`. The agent keeps thin `_sanitize_tool_pairs`/`_is_blocked_by_plan_mode`/`_is_readonly_bash`/`_format_tool_call`/… methods that **delegate** into these, preserving the historical class surface the unit tests build against (`LangGraphAgent.__new__(...)` + `LangGraphAgent._…`) and the `getattr(agent, "_sanitize_tool_pairs", …)` call in `AgentConversationManager`. When adding pure tool/plan/message logic, put it in the collaborator and delegate — don't grow `agent.py`.

**`message_codec` has one hard invariant: the round trip is IDEMPOTENT.** It isn't a display helper — `session_log` encodes every turn with it and `resume_session`/`load_conversation` decode the whole transcript back, then `seed_history` re-encodes ALL of it into the new session file. So one resume is a full decode→encode cycle over the entire conversation, and an asymmetry doesn't show up as a wrong message, it shows up as **growth once per resume**. Decoding used to build the `ToolMessage` from `str(result["content"])` — the `toolResult.content` BLOCK LIST — so a result came back as the Python literal `"[{'text': …}]"`; re-encoding wrapped that string in a fresh `{"text": …}` block, escaping every quote and backslash in it. Because the escapes are themselves escaped next time, each cycle roughly DOUBLES the payload: a 31-char result measured 4,735 chars after ten round trips, and in a real resumed session `fs_read` results reached **1,071,209 chars** — 2.7× past `MAX_TOOL_RESULT_CHARS`, which can't catch it because the cap is applied once at the source (`tool_formatting.truncate_tool_result`) and never re-applied on restore. The visible symptom was `[Context: 12650351 tokens]` on a resumed session (a 21M-char, 1929-message transcript whose tool results were ~90% backslashes) followed by an immediate context overflow. Three pieces: `_tool_result_text` READS the blocks on decode (text concatenated, a `json` block JSON-dumped, unknown blocks JSON-dumped — never repr'd); `_tool_result_blocks` maps list content block-by-block on encode; and `_collapse_wrapped_tool_result` repairs the nested form still sitting in transcripts on disk, so an existing session shrinks ~10× on the next resume and re-seeds clean (measured on the reported file: 20,995,957 → 2,085,848 chars). The collapse is deliberately strict — it unwraps only a literal that is EXACTLY one dict with the single key `text` and a `str` value, so a genuine payload that merely starts with `[{` is untouched — and bounded by `_MAX_COLLAPSE_DEPTH` (64). Nesting grows exponentially, which is also why the bound is unit-tested by lowering it rather than by constructing 64 layers (the first attempt hung the suite trying to build 200). `tests/unit/test_message_codec.py` asserts stability over 50 cycles; a new field on either side of the codec needs the same check, since the defect is invisible in a single turn.

A second group takes the **agent as its first argument** rather than being pure, because it needs the agent's own methods and must stay overridable by a `__new__` test stub: `confirmation_gate` (the destructive-tool confirm gate) and **`tool_loop`** (`run_tool_calls` — the one model↔tool execution loop, shared by `_execute_tools` and `_run_worker_loop`; see its row above for the gate ordering and the one-`ToolMessage`-per-id invariant). Anything touching how a tool call is gated or answered belongs in `tool_loop`, where **both** chokepoints get it — that is the whole point of the module: the two hand-maintained copies it replaced had already drifted apart in ways that only showed up in the worker path.

### Tool hooks (`client/hooks.py`, mounted in `client/agent/tool_loop.py`)

**What it is.** A hook is a shell command the user declares in `~/.mnemoai/hooks/hooks.json` and the app runs around a tool call — for the things a prompt cannot reliably enforce: format every file that gets written, refuse writes under a path that must never be touched, auto-approve the read-only commands the user is tired of confirming, hand the model a hint when a tool fails. Three events, all on the tool boundary: `PreToolUse` (before the call), `PostToolUse` (after it succeeded), `PostToolUseFailure` (after it raised). A `matcher` globs the TOOL NAME (`fnmatch.fnmatchcase`, so `fs_*` / `execute_bash` / `*`), and `type` is `command` only.

**Gate order — below the existing gates, never above them.** This is the security property, not a detail: server-side safety floor (`safety/bash_policy`, `safety/path_policy`, `read_state`) → plan-mode hard block → **`PreToolUse` hook** → `_confirm_tool` → the tool runs. So a hook's `deny` is honored anywhere, but its `allow` reaches exactly ONE gate: it satisfies the confirmation prompt for that single call. It cannot unblock a tool plan mode blocked (the block is above it, so the hook isn't even consulted — asserted in `tests/unit/test_tool_chokepoints.py`), and it cannot reach the floors, which live in the MCP subprocess and would still refuse a catastrophic command. A config file must not be a way to widen what the app may do. Within one event a `deny` also beats an `allow` regardless of file order (the first deny short-circuits; an `allow` never does), because the safe answer must not depend on which hook was written first.

**One mount point.** `run_tool_calls` is the single model↔tool loop for both chokepoints (1.8.6 collapsed them), so the whole feature is three calls in `tool_loop`: `agent._run_hooks(PRE_TOOL_USE, …)` above the confirm gate, and `POST_TOOL_USE` / `POST_TOOL_USE_FAILURE` on the two answer paths, whose `additionalContext` is appended to the `ToolMessage` as `[Hook] …` by `_with_context`. `agent._run_hooks` is the thin delegator (session id from `session_log`, `cwd` from the process, prints `Outcome.notices` via `turn_view.render_hook_notice` unless `quiet`); `agent._hook_deny_message` is the model-facing text, worded so a standing rule isn't read as a transient failure ("do not retry the same call") — the failure mode where a model burns the turn re-calling a blocked tool.

**App home only, and snapshotted at startup.** Both are deliberate departures from steering (which is read-only text, re-read every turn, happily per-project). A `hooks.json` arriving with a `git clone` would be remote code execution on the first edit in that repo, so nothing outside the app home is read (`paths.hooks_config_path()`, no per-project tier, no `$PWD` lookup). The snapshot is the same argument one step on: `active()` caches the `Registry` under a lock (hooks fire from tool-calling threads — parallel orchestrator waves, background sub-agents), so editing the file mid-session cannot change what is already running; a restart applies it, and `/hooks` says so.

**Never blocking, never interactive.** A hook that exits non-zero for any reason other than `DENY_EXIT_CODE`, fails to start, or overruns its `timeout` is reported as a notice, logged, and skipped — the tool proceeds. A slow or broken hook must not be able to wedge a turn, which is the failure mode that gets a hooks feature deleted rather than debugged. And nothing here can prompt: hooks run on tool-calling threads with no terminal, the same constraint `ask_user_question` obeys when headless. stdout that isn't JSON is a user-visible notice only; a successful hook's stderr is logged at DEBUG (how you debug a hook) and stays out of the scrollback.

**Wire protocol.** stdin gets one JSON object (`session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, and `tool_response` on the post events), with long `tool_input` string values clipped to `_MAX_INPUT_VALUE_CHARS` and the clipped keys named under `_truncated` (an `fs_write` body can be megabytes). `MNEMOAI_HOOK_EVENT` / `MNEMOAI_TOOL_NAME` are exported for one-liners that don't want to parse. Answers: `exit 2` denies (stderr, else stdout, else a fallback, becomes the reason), or stdout JSON with `decision`/`permissionDecision`, `reason`/`permissionDecisionReason`/`systemMessage`, `additionalContext`. Everything the model can see is capped (`_MAX_CONTEXT_CHARS`, `_MAX_REASON_CHARS`) since it is per-turn cost.

**Delivery.** No `config.yaml` toggle — presence of the file is the switch, so nothing depends on a user editing a pre-existing config. `seed_example_files()` seeds `hooks/hooks.json.example` (a commented, working example) and `_refresh_example` keeps it current on upgrade; the live `hooks.json` is NEVER created by seeding, because creating it would mean shipping executable rules nobody asked for (`tests/unit/test_paths.py`).

### User-defined slash commands (`client/user_commands.py`, expanded in `client/ui/chat_interface.py`)

**What it is.** A prompt the user retypes, saved as a file: one `*.md` per command under `~/.mnemoai/commands/`, the file stem being the token typed after the slash (`review.md` → `/review`). Optional frontmatter (`description`, `argument_hint`) documents it; the markdown body IS the prompt. Presence of the file is the switch — no config toggle, no registration step.

**Substitution.** `substitute(body, arguments)` fills `$ARGUMENTS` (everything after the name) and `$1`…`$9` (whitespace-split words) in ONE `re.sub` pass, so a substituted value is never re-scanned and an argument containing `$1` stays literal; `$12` is deliberately left alone rather than half-rewritten as `$1` + `2`. A missing positional becomes empty (a command must still run when called with fewer args than it references). **A body that references no placeholder gets the arguments appended** — the common shape is a one-line instruction plus a target, and silently discarding what the user typed is the one outcome that reads as a bug.

**Where expansion happens, and why there.** In `chat_interface._dispatch`, **after every built-in branch** and **before** the empty-line branch: a file can therefore never shadow `/save` or `/plan` (and a file that tries is rejected at scan time with a reason, since the dispatcher would never reach it), while an unknown `/thing` falls through unchanged and still reaches the model as prose. `_expand_user_command` returns the expanded prompt and the rest of `_dispatch` runs as if the user had typed it — **the model never learns a command was involved**, which is what keeps the turn ordinary (routing, episodic storage, the transcript). The one visible trace is a dim `turn_view.render_command_expansion` line (`⌘ /name · file.md`), because the answer otherwise belongs to a question that appears nowhere on screen or in `/export`.

**Tolerant, memoized scanning.** `UserCommandStore._scan()` is the only reader: it skips `_`/`.`-prefixed files (notes, drafts, the bundled `_README.md`) and turns every other unusable file into a `CommandIssue` with a reason — bad name, built-in shadow, unreadable, over `_MAX_BODY_CHARS` (40k), invalid YAML, empty body — printed via `print_error` and listed by `/doctor`, since an invisible command is indistinguishable from an unimplemented feature. Results are memoized process-wide keyed on `_dir_signature` (per-`*.md` name + `st_mtime_ns`), so an edit applies to the very next line typed while the `/` completion menu can re-read the store per keystroke for free. Frontmatter is OPTIONAL here (unlike a skill, whose description is what the model routes on): a plain markdown file is a valid command, described by its first body line.

**Layout coupling.** Two consumers render commands in fixed-width UI, so the store clips `description` (80) and `argument_hint` (40) where they are read from disk, and `chat_interface._user_command_group` clips again to the **built-ins' own column widths**: `_command_box` pads both columns to their widest member and widens the frame to its longest row, so one verbose user description would push the entire command reference past 80 columns. A label that only fits without its hint keeps the NAME (that's the part you type; the hint still shows in the `/` menu, which is open exactly when you're about to type the arguments). The group caps at `_MAX_USER_COMMAND_ROWS` (6) with a `… +N more` row so a user with 30 commands can't push the built-in reference off screen.

**Reserved names live in the store, not the UI.** `BUILTIN_COMMANDS` is `UserCommandStore`'s default `reserved=`, so pure file logic answers "is this name taken" and `/doctor` can count commands without importing the terminal UI. The two lists are pinned together by a test (`tests/unit/test_user_commands.py::TestReservedNames`), because a built-in added without reserving it would let a same-named file load and never fire.

**App home only, deliberately.** Like `agents/` and `skills/` and unlike per-project steering: a command is invoked by the USER, so a `git clone` must not be able to redefine what a name they type expands to. Delivery follows the per-item seed-if-absent rule with a pristine-only refresh (`_PRISTINE_BUNDLED_COMMAND_HASHES`, `_refresh_pristine_command`): the bundled `explain.md` and `_README.md` reach an already-populated install on upgrade, and a file the user has edited is never touched.

### `@`-file mentions (`client/file_mentions.py`, completed in `client/ui/tui.py`, expanded in `client/ui/chat_interface.py`)

**What it is.** The user pointing at a file. `@path` typed anywhere in a line completes as you type, and on submit each one is read and **appended to the prompt** under its own header (`Contents of /abs/path (mentioned as @path):`) — the content is present whether or not the model would have decided to look for it, which is the whole difference from typing the path in prose. The module is pure file logic (no MCP, no LLM, no prompt_toolkit) precisely so the completer and the dispatcher share it: what the menu offers and what actually attaches cannot disagree.

**One syntax, shared with steering.** `expand(text, cwd=None)` scans with `steering_store.references()` instead of a second regex, so `@`-references mean the same thing in a prompt and in a `STEERING.md` — including the fact that a ref which doesn't resolve to a readable path is **left in the prose**, which is what makes `@staticmethod`, an `@handle` and an email address harmless. Only a ref that _looks_ like a path (`_looks_like_a_path`: contains `/`, or a dot that isn't leading/trailing) earns a gray `no such file`; everything else produces no output and no notice. `resolve(ref, cwd)` is local rather than steering's because it differs on the two points that matter: a relative ref is anchored to the **prompt's** working directory (a steering ref belongs to the file that wrote it), and a **directory** resolves too.

**Return shape.** `(text, [Mention])` where `Mention(ref, path, kind, chars, summary)` has `kind` ∈ `file` | `dir` | `missing` | `skipped`, `.attached` (did this put anything in the prompt) and `.label` (`@src/x.py · 412 lines`, the one line the UI prints). A directory contributes `_dir_listing` — names only, `/`-suffixed for dirs so they can be re-mentioned — never its files' content; the listing is bounded at `_MAX_DIR_ENTRIES` (200) while the summary counts the directory in full, so "11 entries" beside a list of 3 is honest.

**Three bounds, because this lands in the USER's message.** Compaction can summarize an inlined file but tool-result eviction can never shrink it, and `MAX_TOOL_RESULT_CHARS` doesn't apply here: `_MAX_FILES` (10 per line), `_MAX_TOTAL_CHARS` (60 000 across the line) and per-file `MENTIONS.MAX_FILE_CHARS` (`_DEFAULT_MAX_FILE_CHARS` 20 000, `0` disables — read through `_max_file_chars()` the way `steering_store` reads `STEERING.MAX_CHARS`, so a new key needs no config edit to reach an existing install). Each overrun is a `skipped` mention with its reason, and a **truncation says so in the prompt** ("only the first N chars … do not assume the omitted part says nothing"), because a silently cut file reads to the model as a complete one. `_read_text` reads `cap + 1` bytes (never the whole file), sniffs the first 8 KB for a NUL (`not a text file`) and decodes with `errors="replace"`. Dedup is on `_key(path)` = `normcase(realpath())`, as steering does, so `@notes.md` and `@./notes.md` attach once.

**A mention is not a read.** `server/tools/read_state.py` still requires its own `fs_read` before `fs_write`/`file_edit` on an existing file. The gate protects against writing over content the model hasn't seen _through the tool that records mtime_; an inlined copy in the prompt carries no baseline and would make a stale-read check meaningless.

**Two completion modes** (`completions(fragment, cwd=None, limit=20)` → `[(path, meta)]`). A fragment containing `/` or starting `~`/`\` completes its **last segment** from the parent directory via `_dir_entries` (`os.scandir`, so a file outside the project is reachable, absolute paths included; an empty fragment hides dotfiles, `.hid` reveals them). A bare fragment matches the **project index by basename** (`@chat_int` → `src/mnemoai/client/ui/chat_interface.py`), ranked by `_rank`: basename-prefix, then basename-substring, then shallower, then shorter, then name. The index is `_git_index` (`git ls-files --cached --others --exclude-standard -z`, 2 s, honors `.gitignore`) falling back to `_walk_index` (bounded: `_MAX_INDEX_FILES` 20 000, `_MAX_WALK_DEPTH` 12, `_SKIP_DIRS`), TTL-cached 10 s per directory in the process-global `_INDEX_CACHE` so a burst of keystrokes costs one scan.

**Every entry point is non-raising.** `expand`, `completions` and `_git_index` swallow their own failures (a vanished file becomes `("skipped", "could not be read")`, a broken scan returns `[]`), because a completer that throws takes the pinned input down with it, and a mention is typed mid-sentence by someone who wants an answer — a failed expansion sends the line exactly as typed.

**UI wiring.** `tui.FileMentionCompleter` is joined to `SlashCommandCompleter` by `merge_completers` — one menu, and only one of them can match a given cursor position, so they never compete for the popup. It defers the matching to `fragment_at_cursor` (`""` for a bare `@`, `None` for no mention under the cursor — the two must stay distinguishable) and `completions`, and yields `start_position=-len(fragment)` so completing replaces only what was typed. `chat_interface._expand_mentions` runs in `_dispatch` **after** the user-command expansion (a command body can itself mention files) and after every built-in (`/save @notes.md` keeps its literal argument), printing one `turn_view.render_mention_notice` line per mention: attaching nothing and attaching the right file look identical on screen otherwise, and the second leaves the model guessing about a file it never saw.

### Workspace reports (`/files`, `/diff`, `/copy`) (`client/file_ledger.py`, `client/diff_report.py`, `client/ui/clipboard.py`)

**What they share.** Three commands about the working tree rather than the conversation, and all three exist because the terminal is not a record: a streamed turn's own account of what it did scrolls away, is interleaved with everything else, and after a compaction is gone from the context entirely. Each follows the `usage_tracker`/`context_report` split — pure `render`, client-taking `report(client)` — and each is **answered locally**: a report that costs a turn is a report nobody runs, so none of them is a tool the model can call.

**The ledger is the shared substrate** (`file_ledger.FileLedger`, held as `agent.files`, reset by `client.clear_context` exactly like the usage tracker). It records `READ`/`WRITTEN`/`ATTACHED` per file and is fed from **one** place — `tool_loop.run_tool_calls`, after a SUCCESSFUL `_invoke_tool` — plus `@`-mention expansion in the UI. That single feed point is the reason it can answer for work nobody watched: a sub-agent's edits and a parallel wave's reads pass through the same loop, so they are in the list without any per-caller wiring. Deliberately narrow: only the three tools that name ONE file (`fs_read`, `fs_write`, `file_edit`) are mapped, since a tree-wide `grep_search` produces no path the user can go and look at. Keyed on `normcase(realpath())` — the read-before-write gate's key — so `./x.py`, `x.py` and an absolute spelling are ONE row with the real counts. Lock-guarded (pool threads), `record` swallows everything (bookkeeping must not break a tool call), and bounded at `_MAX_ENTRIES` with the excess **counted** rather than dropped silently.

**It is a ledger, not a context inventory.** A file read an hour ago may have had its result evicted or its turn summarized away since. The ledger still lists it, because "we looked at this" stays true — and the report says so in its footer instead of implying the content is still in the window, which is the one way this report could mislead.

**`/diff` is `git status` plus the column git cannot produce.** `git status` cannot say which of twelve dirty files came from THIS conversation; `file_ledger.changed_paths()` can, so `collect` marks those `mine`, sorts them first and legends the `✎`. Everything unmarked was already dirty when the conversation started, which is the distinction that decides what is safe to commit. One `git diff --numstat HEAD` covers staged and unstaged together; untracked files come from `git ls-files --others --exclude-standard` and are counted locally by `_count_lines` (NUL byte, or over `_MAX_UNTRACKED_BYTES` → reported as `binary` rather than read).

**Read-only by construction, not by convention.** The only git verbs in the module are `rev-parse`, `diff` and `ls-files`, and `tests/unit/test_diff_report.py::test_no_git_invocation_can_write` regexes every `_git([...])` argv **in the source** and asserts the verb is one of those three — so a mutating verb can't be added later without failing the suite. Everything is bounded (`_MAX_ROWS`, `_MAX_DIFF_LINES`) and wherever output is cut the exact `git` command that shows the rest is printed, since a truncated diff that doesn't say how to see the whole thing just moves the problem.

**Two numstat shapes break naive parsing** and both are handled in `parse_numstat`/`_numstat_path`: a binary file's counts are `-`/`-` (not integers), and a rename arrives as `old => new` or `dir/{old => new}/x.py` — the braced form has to be rebuilt, not split. **And an empty `git diff` is ambiguous:** a committed file that hasn't changed and a file git has never seen both produce nothing, so `_is_tracked` (`git ls-files -- <rel>`) separates them; without it every unchanged file rendered as brand new and all-additions. One more display detail worth keeping: `_counts` returns `(plain, colored)` because ANSI occupies no columns — padding the colored string ragged-ends the counts column.

**`/copy` exists because mouse selection copies the terminal's wrapping**, not the answer. Extraction is pure and kept separate from transport: `answer_text` walks back to the Nth assistant message that actually has prose (tool-call-only turns and `ToolMessage`s skipped, block lists flattened) matching on `isinstance(AIMessage)` — a streamed reply is an `AIMessageChunk`, and the class-NAME check is the bug that once exported a transcript containing no answers. `last_code_block` returns the last fenced block and its language, including an **unterminated** fence: the code is on the screen, so refusing to copy it would misdescribe what's there.

**The transport ORDER is the design.** A local helper (`pbcopy`/`wl-copy`/`xclip`/`xsel`/`clip.exe`) and **OSC 52** (which asks the terminal itself to set the clipboard) are both tried, but **over SSH the terminal goes first** — a helper on the far end would set the clipboard of a machine nobody is sitting at, which is precisely the case OSC 52 exists for. Inside tmux or screen the sequence needs the same DCS passthrough as OSC 9, which is why `notify.wrap_for_multiplexer` is public rather than copied: a second implementation is a second place to get the ESC doubling wrong. An oversized payload is **refused, not truncated** (a half-copied answer is worse than a failed copy), the notice names what/how big/which transport because a clipboard write is invisible until you paste, and with neither transport available it points at `/export`. Note the test-only subtlety: the module reads `sys` through itself, because pytest's capture re-assigns `sys.stdout` at the start of the call phase and would undo a fixture-level patch of the attribute.

### Curated memory (MEMORY.md) (`client/memory/memory_store.py`, `server/tools/memory_tool.py`)

A small, bounded, profile-scoped (shared across models) `~/.mnemoai/{profile}/MEMORY.md` of durable facts (user/environment details, conventions, lessons, tool quirks, completed work) that the agent **curates itself** via the MCP `memory` tool (`add`/`replace`/`remove` over a list of entries separated by a Markdown `---` rule — legacy `§`-delimited files still parse and migrate to `---` on next write; logic in `MemoryStore`). It is injected **whole** into the system prompt at session start by `_build_system_prompt`/`_inject_memory_context` in `client.py` (a frozen snapshot — writes during a session apply next session). A hard char cap (`MEMORY.MAX_CHARS`, default 2200) forces the agent to consolidate (merge/remove) instead of growing unbounded. The tool prompt guides the model to tag each entry with one of four kinds — `[user]`/`[feedback]`/`[project]`/`[reference]` — and to skip anything the repo/git/CLAUDE.md already records (a tagging convention only; storage stays a single flat file). Distinct from episodic memory (similarity-retrieved per query) and the ACE playbook (tool strategies); it complements both. Gated by `ENABLE_MEMORY` (default true). The `/memory` command views it (`/memory clear` wipes it); writes are confirmation-gated when `REQUIRE_MEMORY_CONFIRMATION` is true (default false — auto-saves), via the same client-side `_confirm_tool()` gate as bash/file writes. **Auto-extraction (opt-in, `ENABLE_MEMORY_AUTO_EXTRACTION`, default false):** the auto-learning counterpart to the tool — `client.auto_extract_memory(query, response)` runs at turn end (wired in `chat_interface` after `reflect_and_learn`, getattr-guarded) on a daemon thread, distilling durable facts from the exchange via the `MEMORY_EXTRACTION_PROMPT` (a one-shot `_invoke_model_once` call that doesn't touch agent state) and applying the returned JSON `add`/`replace` ops through `MemoryStore`. Unlike the tool path it writes **without** a confirmation prompt (hence its own opt-in toggle) but is confined to `MEMORY.md`; `_parse_memory_ops` is tolerant (bad output → no-op) and the worker never raises.

### Steering (STEERING.md / CLAUDE.md) (`client/memory/steering_store.py`, `utils/paths.steering_files`)

**User-authored, always-on instructions** — the counterpart to the agent-curated `MEMORY.md`. Discovered hierarchically (`steering_files`): the app home plus every directory from the CWD **up to the repo root** (first ancestor with `.git`; with no `.git` anywhere the walk stops below the home dir rather than at the fs root, so a stray `~/CLAUDE.md` can't become always-on for every non-git directory — an explicit `.git` AT `$HOME`, i.e. a dotfiles repo, still counts), concatenated broadest→most-specific, each under a `Contents of <path>:` header (`SteeringStore.read`, read-only — the agent never writes it, the key difference from `MemoryStore`). Injected as a leading **`<steering>`** block prepended to the prompt **every turn** by `client._steering_reminder()` in `query()` (with an "these instructions OVERRIDE any default behavior" framing), then **stripped before storage** by `_strip_ephemeral` (the shared ephemeral-block regex, same rail as the plan-mode banner). Consequences: it's **re-read from disk each turn** (edits apply immediately, no restart) and **never enters history**, so compaction can never summarize it into a lossy paraphrase — it always reaches the model verbatim. This is the same guarantee an always-on instructions file gets by living outside the summarized conversation. **No config toggle** — its presence _is_ the switch (no file → nothing injected), so there's nothing to enable. No dedicated slash command (edit the files directly); distinct from `MEMORY.md` (agent-curated facts), skills (on-demand procedures), and `prompts.yaml` (the base system prompt).

**Two accepted filenames** (`paths.STEERING_FILENAMES = ("STEERING.md", "CLAUDE.md")`, applied by `instruction_file_in(directory)`): a repo that already carries agent instructions under the widely-used `CLAUDE.md` is picked up with no second file and no config. **Each directory contributes AT MOST ONE file** — the first name that exists wins, so a `CLAUDE.md` beside a `STEERING.md` is skipped rather than concatenated (which is what lets a project keep both and steer this assistant separately, and bounds the per-turn cost at one file per tier). **The shadowing is per-DIRECTORY, never global** — this is the invariant to preserve: finding a `STEERING.md` in one tier must NOT switch `CLAUDE.md` off for the others, or a global `CLAUDE.md` silently stops applying the moment a project adds a `STEERING.md`. Both directions are unit-tested (`test_shadowing_is_per_directory_not_global` and `test_a_global_steering_md_does_not_suppress_a_project_claude_md` — a global-shadowing implementation passes the first and fails the second, which is why both exist). Two further details: **reading accepts either name but `global_steering_path()` — the authoring target — stays `STEERING.md`**, so the creator skill can't be talked into writing the fallback name; and **de-dup keys on `normcase(realpath(...))`, not the spelling**, because `app_home()` is returned unresolved while the project walk resolves, so one file reached under two spellings (a symlinked home inside the walked chain) would otherwise be injected twice — paying double context and stating every rule to the model twice. **Nothing outside the app home is read for the global tier** (no `~/.claude/CLAUDE.md`): a file another tool owns and rewrites must not silently become this assistant's always-on instructions.

### Session transcripts + `--resume` (`client/session_log.py`, `utils/paths.sessions_dir`)

**Automatic** append-only transcripts, scoped to the launch directory — the counterpart to the **user-curated** `/save`+`/load` (untouched, stored in `{profile}/conversations/`, and NEVER swept).

**Storage.** `{profile}/sessions/{sanitize_cwd(cwd)}/session_<ts>_<pid>_<rand>.jsonl`. `sanitize_cwd` collapses everything outside `[A-Za-z0-9]` to `-`, truncating at 120 chars with an 8-hex suffix of the FULL path so two deep sibling directories can't collide into one dir. The id carries a random suffix because `<ts>_<pid>` alone collides when two sessions start in the same second (rapid relaunch), which would append two conversations into one file. One JSON object per line: `meta` (session id, cwd, started, model), `turn` (`n`, `ts`, the strands-encoded messages that turn added), `compact` (the `messages` kept live + a `summary` when older turns were summarized away — a checkpoint, see below), `restore`, `label`.

**Write path.** `client._attach_session_log()` sets `agent.session_log` in `start()` (skipped entirely when `SESSION_MAX_AGE_DAYS <= 0`). `LangGraphAgent.invoke()` buffers the turn's messages in a local `turn_log` and flushes ONCE through `_log_turn` — deliberately NOT an index-slice of `_messages`, because pre-flight compaction runs mid-turn and replaces that list, invalidating any index taken at the top. Encoding reuses `message_codec.convert_langchain_messages_to_strands`, the same codec `/save` uses, so a resumed session decodes identically to a loaded one.

**The transcript must never diverge from live history.** Every way a turn can end has to write: the normal return, the `KeyboardInterrupt` cancel, the `GraphRecursionError` limit, AND a generic `except Exception` (dropped provider connection, MCP failure, a bug) that logs `_commit_turn(result, turn_log)` when a snapshot survived, else the bare `turn_log`, then re-raises. Rationale: whatever the turn produced STAYS in `_messages` and the user keeps talking, so a log that skips the failed turn silently stops at the last SUCCESSFUL turn while the conversation runs on — observed in the wild as a 408-message chat whose transcript held 64 messages (`--resume` restored a stump even though `/save` had everything). It was invisible because `_log_turn` swallows its own errors at debug level. `_last_input_tokens` is reset on this path too, since the count is stale once the turn is abandoned.

**Restored history is seeded into the new session file.** `SessionLog.seed_history(messages, source)` writes ONE `restore` record, called via `client._seed_session_log` from BOTH `resume_session` and `load_conversation` (they replace live history wholesale, so without it the new file records only what follows the restore — resuming _that_ file would replay a fragment of a conversation visible in full on screen, and each resume-of-a-resume truncated the chain further). The source file is **never mutated**, so the same point can be resumed repeatedly. `read_session` replays `restore` records in order but counts only `turn` records toward `turns`, which keeps two things honest: the picker's "N turns" means turns taken in THAT session, and a resume nobody typed into still reads as empty — so `list_sessions` skips it (it would otherwise appear as a duplicate row of the session it restored, one more on every no-op resume) and `discard_if_empty` removes its file at exit.

**A restore reproduces the state the session ENDED in — compaction included.** Append-only is a property of the FILE, not of what comes back: the transcript keeps every turn's full text (so nothing said is ever lost from disk), but replaying all of it rebuilt the raw history a `/compact` had already summarized away. Measured on a real conversation: `[Context: 235793 tokens]` before closing, `[Context: 1166221 tokens]` after `--resume` — 5× larger, past the model's window, before a single new message — so the first turn back had to summarize the whole chat again and the summary already paid for was thrown away (both the 11:22 and the 11:52 session in that chain restored ~2,000 messages and re-compacted within ~11 minutes). `log_compaction(summary=…, kept=…)` therefore records a **checkpoint** instead of a bare marker, and `read_session` splits the two questions it answers: **`messages`** is what to RESTORE (a checkpoint rewinds it to the kept window, and `compacted_away` says how many messages the summary stands in for), **`all_messages`** is everything logged — what the replay, the picker preview and `exchanges` read, so a compaction can never shorten how a conversation is displayed or sized (a `/rewind` is the one record that narrows this list too, because a withdrawn exchange did not happen; see **Rewinding a turn** below). `client.resume_session` restores `messages`, replays `all_messages`, and calls `conversation_manager.apply_restored_summary`, which rebuilds the system prompt through the SAME `_build_system_with_summary` a live compaction uses (so the session-start blocks come back with it) and sets `previous_summary` — without which the NEXT compaction's reduce step would silently drop this history. `/load` and `/branch` go through the same call; `seed_history(…, summary=…, kept=…)` re-states the checkpoint in the new file, so a resume-of-a-resume doesn't re-inflate, and `branch_session` copies a checkpoint only when the branch point is AFTER it (branching before it is a deliberate rewind to the raw history). Three couplings fall out of this: `list_sessions` judges emptiness and builds its preview from `all_messages` (a checkpoint can leave `messages` empty in a conversation that is very much real, and the kept window no longer holds the opening prompt); `/save` records `summary_text` as its own key and `/load` re-wraps it (persisting the wrapped `<conversation_summary>` block would nest a block inside a block); and `clear_context` nulls BOTH `previous_summary` and `summary_text`, else a cleared conversation's history reaches the next summary and the next `/save`. A `compact` record with NEITHER key — every one written before 1.12.6, plus the fallback when the kept window can't be encoded — keeps its old purely-informational meaning and restores everything, which loses only the optimization.

**The context shrinks two ways, so `messages` marks a checkpoint, not `summary`.** A summary replaces older turns; **tool-result eviction** — the cheap no-model-call layer that runs first on every compaction path — drops no message at all, it rewrites old results smaller. There is nothing to summarize, yet the state it leaves is just as unreachable from the raw turns, which hold every result at its ORIGINAL size: eviction that brought the estimate back under the high-water mark returned without logging anything, so the next resume replayed the full-size results and handed back exactly the tokens eviction had reclaimed — the defect a summary checkpoint had fixed one release earlier, in the layer that runs more often. `client._log_eviction_checkpoint` writes `log_compaction(kept=…)` (no summary) from `_compact_now`'s eviction-only branch — deliberately NOT when eviction falls through to `_compact`, which writes its own; a second record there would duplicate the entire history for nothing — and is best-effort, since by that point the live context IS smaller and raising would turn a successful compaction into a failed turn. Two things follow. An eviction record must **not clear** a summary an earlier compaction left standing, so `read_session` and `branch_session` update `summary` only `if "summary" in rec`. And since eviction drops no message, `compacted_away` is 0 for it — neither it nor `summary` can tell a caller that `messages` is narrower than `all_messages` — so `read_session` also returns **`checkpoint: bool`**, and every restore path passes `kept=` to `seed_history` only when that flag is set (passing it unconditionally would copy the whole conversation into the new file as a fake checkpoint of itself).

**Picker labels show what the USER typed.** `first_user_prompt(messages, max_len)` is the single shared extractor — used by `list_sessions._preview` AND by `client.conversation_title` for the `/load` dialog, so both surfaces label the same chat identically. It strips the ephemeral `<steering>`/`<plan-mode-active>` blocks (via `LangGraphAgent._strip_ephemeral`), the prepended `[Episodic Memory …]` block (kept only the prompt after the `\n\n`), tool-result-only messages, and auto-delivered background sub-agent reports — falling through to the next user message when one yields nothing, so a session whose first turn was pure injection is still labelled by its first real prompt. `max_len` is the TOTAL width including the ellipsis (callers size it to a column budget). Unstripped, several unrelated sessions all rendered as `[Episodic Memory - Similar Past Tasks] 1. "hello" → no tools …` and none could be told apart.

**Naming a session (`/rename`).** The picker otherwise labels every row with its first prompt — the one thing a resumed conversation and its parent have in common — so after a few sessions in one project the rows stop being distinguishable. `SessionLog.set_label(title)` appends a `label` record (the file is never rewritten, so renaming twice leaves two records and `read_session` resolves it LAST-WINS; an empty title is a valid record that clears the name back to the preview), bounded to `_LABEL_CHARS`. A `label` is **not a turn**: it can't make a turn-less session resumable and doesn't save its file from `discard_if_empty`. `list_sessions` carries it alongside `preview`, and `main._format_session_label` prefers it while keeping the `(branch @ turn N)` / `(continued)` tag. **It survives a resume but not a branch:** `client._seed_session_log(..., label=…)` re-stamps the name into the new file (a resume continues the SAME conversation, so losing the name on the first resume would defeat naming it), while `branch_session` copies only `turn`/`restore` records — a fork already inherits its parent's opening prompt, so inheriting the name too would put the two rows back to identical. `client.session_label()` / `client.rename_session(title)` (whitespace-normalized) drive `/rename`, which distinguishes "no name yet" from "nothing is being recorded".

**Read path.** `read_session` tolerates a truncated final line (a killed process) by skipping unparsable lines, so one bad write can't make a session unreadable. `list_sessions` sorts by mtime descending, skips sessions with no completed turn (resuming one would restore nothing), and caps at `limit` (20) — the cap bounds what's **offered**, never what's kept. `main._resume_session` resolves `"pick"` / `"latest"` / an id (exact, then suffix match) and calls `client.resume_session`, which clears+extends `agent.messages`, strips any stored `<plan-mode-active>` block, and replays via `turn_view.render_conversation` — the same path as `/load`. It deliberately does NOT set `current_conversation_path`: a resumed session is not an open `/save` file, so a bare `/save` afterwards must not overwrite one.

**Three UX rules the flow enforces** (each was a bug first):

- **`_resume_session` returns a three-way outcome, not a bool** — `"exit"` / `"resumed"` / `"fresh"`. Cancelling the picker returns `"exit"` and `main()` **returns without starting the chat loop**: `--resume` is a request to resume, so falling through to a fresh chat both surprises the user and leaves another empty session behind. `"fresh"` (no sessions in this dir yet) must NOT be conflated with `"resumed"` — the caller uses it to decide whether the banner still needs printing.
- **The banner prints BEFORE the transcript.** `run_chat_loop(welcome=…)` can skip its own banner because `_resume_session` calls `chat_interface.show_welcome()` first, so the restored conversation lands directly above the prompt (logo → conversation → prompt). Printing it after the resume pushed the whole replayed conversation above the logo.
- **Turn-less sessions are deleted at exit.** The `meta` record is written at startup, before we know whether the user will type anything, so a launch they immediately quit (or a cancelled `--resume`) leaves a file with no turns. `SessionLog.discard_if_empty()` (called from `main._discard_empty_session` on both exit paths) unlinks it — but only after re-reading the file and confirming zero `turn` records, so it can never remove a session another process wrote. **Turn-less is not the same as worthless:** a file whose own records PIN a narrower state (`_pinned_state` — a compaction checkpoint written here, or a `/rewind` rebase) is kept, because that state exists nowhere else; a resume → `/compact` → quit-without-a-turn used to unlink the file, and the next resume re-inflated the whole pre-compaction history from the parent.

**Expiry.** `sweep_old_sessions(SESSION_MAX_AGE_DAYS)` at startup (root-level config key, default 30, `0` disables recording entirely). It sweeps **every** project dir, not just the current one — otherwise a directory you stopped working in would keep its logs forever — and removes a project dir once its last session ages out. Only `session_*.jsonl` is touched, so `/save` files and anything else are safe.

**Deliberate exclusions.** Sub-agents are not logged (they run on an isolated `worker_messages` list that never enters `_messages`; logging them would interleave a second conversation into the chain). A **cancelled** turn IS logged, including the `INTERRUPTED_MARKER`, so a resumed session shows exactly what the live one did. Every write is wrapped best-effort — a transcript is a convenience and must never break the turn the user is waiting on.

### Rewinding a turn (`/rewind`) (`client/rewind.py`, `client.rewind_turn`)

**The third way to shrink the context, and the only one that is an UNDO.** `/clear` throws the session away, `/compact` summarizes it; neither takes back one thing. Sometimes the prompt itself was the mistake — a wrong file, a wrong framing, a question that sent the whole turn down a path you don't want in the context — so `/rewind` drops the last prompt **and everything the turn produced**, leaving the conversation as it was the moment before Enter.

**Where the turn starts is not "the last `HumanMessage`".** A `role: user` message can be a tool result or an auto-delivered background sub-agent report, and the per-turn injections (steering, the plan reminder, the episodic block) are prefixes ON a real prompt rather than messages of their own. `boundary(messages)` therefore walks back for the last message where `turn_view.user_prompt_text` leaves something behind — the same rule the reflector uses for a turn boundary and the `--resume` picker uses for a label — and everything from that index on is dropped in one `del`.

**It moves the conversation only; files on disk are never touched.** The boundary `/branch` draws, and the reason this is deliberately not a checkpoint/restore feature: undoing an edit is `git` (or `/diff`) territory, and a command that half-undid a turn — context rolled back, files not — would be worse than one that says which half it does. Two things it also leaves standing, because both stay TRUE after a rewind: the **read-before-write registry** records that a file was read at mtime _T_, which is a staleness guard rather than a record of what's in the context (the file is still at _T_, so un-recording it would only make the model re-read a file it correctly saw), and the **`/files` ledger** is a ledger — "we looked at this" happened, and its own report already says a listed file may have left the window.

**It refuses rather than half-succeeds.** The graph state and the transcript are both append-only, so a summary that already stands for the withdrawn turn cannot be un-summarized: `last_live_turn(path)` reports whether a compaction landed on or immediately before that turn (a seed-adjacent checkpoint excluded — that one belongs to the restore, not to this turn) and the command declines with the reason, naming `/compact` as the irreversible one of the pair. It also declines when compaction has summarized every prompt of the user's away, since there is then no boundary to cut at.

**A withdrawal is a RECORD, not a deletion — and it has two shapes** (`SessionLog.log_rewind`). A turn taken in THIS session is withdrawn **by number** (`{"t": "rewind", "n": 4}`; `_turn` is decremented so `_withdrawn_turns` resolves a repeated number to the most recent turn still carrying it, newest-first). An exchange that arrived inside a `restore` blob — after `--resume`/`--continue`/`/load` — has no `turn` record to skip, so the record instead pins **the history that survived** (`{"t": "rewind", "messages": […]}`, a **rebase**): without it the withdrawal held for the running session and the exchange came back at the next resume. The withdrawn text stays on disk, which is the point — an undo of the conversation, not a redaction of the file. A rebase whose non-empty input encodes to nothing is a FAILURE, not a rewind to zero, and is not written.

**A rewind narrows BOTH of `read_session`'s lists** — the one place it differs from a compaction, which narrows only `messages`. A withdrawn exchange did not happen, so the replay, the picker preview and `exchanges` must not show it; the by-number shape gets that for free by skipping the turn record, so the rebase shape has to do it explicitly (it is sound because a rebase is only written when no live turn record is left, so `all_messages` is the seeded blob and `kept` is what survived of it). `branch_session` skips withdrawn turns too — a fork must not resurrect what `/rewind` took back — and `turn_summaries` offers none of them as a branch point.

**Both halves of the file's survival needed the pinned-state flag.** A rebase leaves a file with zero turns whose only content is the narrowed state, and it was being dropped twice over: `discard_if_empty` unlinked it at exit, and `list_sessions` skipped it for having no turns — which offered the PARENT instead, the one file still carrying the exchange the user had just withdrawn (observed live: the withdrawn prompt reappeared after `--continue`). `_pinned_state` exempts it from the first and `read_session`'s `checkpoint` flag from the second; a checkpoint merely re-stated by `seed_history` (`log_compaction(seeded=True)`) sets neither, since the parent owns that state and an unused resume file must stay discardable.

**What a rewind cannot take back is what the session LEARNED.** An episodic entry, a playbook strategy, an auto-extracted `MEMORY.md` fact — those writes are lossy by construction: `store_episode` de-duplicates against what is already there and `PlaybookStore.append` folds a repeat strategy into an existing entry by raising its confidence, so there is no entry to delete, only a learned signal to do arithmetic on. `learning_sinks(client)` names the stores that are actually enabled (naming a disabled one would invent a consequence) and the notice states it plainly. Finally the command nulls the cached provider token count (`_forget_context_size` — it measured the history that just shrank) and `previous_query`/`previous_response`/`previous_messages`, because the legacy episodic path evaluates the PREVIOUS prompt on the next one and would otherwise store the withdrawn exchange as an episode.

### Agent Skills (`client/memory/skill_store.py`, `server/tools/skill_tool.py`)

Authored, on-demand instruction packs, one per directory: `~/.mnemoai/skills/{name}/SKILL.md` (YAML frontmatter with `name`+`description` required and an optional `argument_hint`, then a markdown body; may bundle `reference.md`/`scripts/`). **Three-tier progressive disclosure:** (1) only each skill's name+description (and `argument_hint`, rendered as `(expects: …)`) is injected into the system prompt at session start — the `<available_skills>` block, cheap and always-on; the whole listing is bounded by `_MAX_LISTING_CHARS` (overflow collapses into a `+N more` line) so a large skills library can't dominate the prompt; (2) the full body is loaded into context **only when the model calls the `use_skill` tool** (its return value _is_ the body, landing as a `ToolMessage`); (3) bundled resources are read/run on demand via `fs_read`/`execute_bash`. The **directory name is the canonical id** (`use_skill(name)`); frontmatter `name` is display only. `SkillStore` is pure file logic (tolerant scan — bad/incomplete skill skipped, never fatal — mirroring `load_external_servers`), shared by the server `use_skill` tool and the client's tier-1 injection (`client._inject_skills_context`) + `/skills` command — the same shared-store pattern as `MemoryStore`. `use_skill` is in `_ALWAYS_AVAILABLE_TOOLS` so a skill-matching query that classifies as `simple_qa` (e.g. "write a commit message") can still trigger it. **Compaction caveat:** `_build_system_with_summary` re-fetches the base prompt fresh (dropping all session-start injections), so it re-injects the `<available_skills>` block via `format_available_skills` (a loaded body lives in the conversation as a tool result and is summarized like any other). Gated by `ENABLE_SKILLS` (default true); a bundled example (`utils/skills_example/`) is seeded on first run. Distinct from MEMORY.md (always-on facts), the playbook (learned tactics), and prompts.yaml (always-on framing): skills are _authored, on-demand procedures_. `/skills` lists them; `/skills <name>` previews a body. Distinct from the enforced plan mode (`server/tools/plan_mode_exit.py` + `plan_policy.py`) and the curated memory tool.

### Terminal UI (`client/ui/chat_interface.py`, `client/ui/tui.py`, `client/ui/turn_view.py`, `client/ui/status_bar.py`, `client/ui/notify.py`)

The chat REPL is a **pinned-input** UI on a TTY (`PinnedPromptReader` in `tui.py`): a persistent, **non-full-screen** prompt*toolkit `Application` keeps the `>` input fixed at the bottom of the terminal while a query runs, and its output — the answer, the styled reasoning/tool blocks — streams **above** it via `patch_stdout(raw=True)` into native scrollback, so **wrapping, scrollback, and copy/paste are preserved**. The query runs on a **worker thread** (required: `client.query()` calls `asyncio.run()` internally, which raises on a thread that already owns a running loop) via `asyncio.to_thread`; the app's event loop stays live to service keystrokes and animate the status line. Key behaviors: **`Ctrl+J`** newline / **Enter** submit; **Esc or Ctrl+C during a turn cancels** it (`_request_cancel` injects `KeyboardInterrupt` into the worker thread → `client.query` returns "Operation was cancelled." — delivered at the next stream-chunk boundary), while Ctrl+C/Ctrl+D twice when idle exits; an **input queue** — a line submitted mid-turn shows a dim `> … (queued)` line in the pinned region and runs as its own FIFO turn after (never a concurrent query, never folded into the running turn), echoed to scrollback (paired with its own answer) only when the worker starts it. (The agent-side mid-turn *steering* machinery — `agent.steer`/`_drain_steering`, drained in `_execute_tools`/`_orchestrate` — is intact but **no longer fed by the UI**: it was retired as the default because a message steered during the final tool-call-free model call was never drained at turn end and leaked into the next turn. It is separate from background sub-agent auto-delivery, which uses its own `drain_background_completions`, not the steer queue.) The animated status line shows `⠙ Thinking… (esc to cancel)` with cycling dots, driven by the app's `refresh_interval` (no `\r` writes — a `SpinnerStatus` **sink** flips state and the pinned line renders it; the `\r` stdout `Spinner` mode is used only by the non-TTY plain loop). Slash completion (`SlashCommandCompleter`) pops a menu whose rows the input window reserves space for via a dynamic height (`_input_height`, mirroring `PromptSession`'s reserve-space-for-menu) so it renders even with the input at the terminal bottom. **Styled turn view** (pinned mode, `agent.styled_turn_view`): reasoning is buffered and shown as a collapsed green-bordered **"Thought for Ns…"** block (`client/ui/turn_view.py`), and tool calls render as **`ToolName` + `↳ arg=value`** blocks instead of the `[⚙ …]` marker (that marker is still used by the non-TTY plain loop). Loaded conversations replay through the **same** `CodeFormatter` (`turn_view.render_markdown`), so a reloaded answer's markdown/code renders identically to a freshly-streamed one. **Confirmations** (`Proceed?`): the worker-thread `_confirm_tool` gate calls an in-app `_confirm_ui` hook that shows the prompt in the pinned region and captures a `y`/`n`/`a` keypress. **Dialog commands** (`/load`, `/config`, `/model`, `/params`, `/features`, `/memory clear`): a nested full-screen app can't run inside the pinned one, so `reader.run_dialog` **exits the pinned app** (terminal returns to cooked mode), runs the command with the normal full-screen dialogs (`tui.select_from_list`, `configurator`'s `\_dialog**`), then relaunches the pinned app; the configurator suppresses its scrollback banner/overview on a TTY (dialogs carry that), leaving only the final outcome line. **Everything degrades to a plain `input()` loop when not a TTY** (`\_plain_loop`), so pipes / CI / the unit suite never block on a modal. **Streamed answer rendering** (`utils/formatting/code_formatter.py`, `CodeFormatter`) buffers the response and **re-parses it with `markdown-it-py`** on each chunk (rendering completed top-level blocks once, re-parsing only the growing tail) rather than scanning triple-backtick deltas with a state machine — so a fenced block's language is consumed by the parser (never leaks as a bare text line), adjacent fences / unterminated fences / half-finished spans resolve on the next chunk, and there's no incremental fence bookkeeping to desync. Code bodies are Pygments-highlighted; headers/lists/quotes/rules and inline \*\*bold\*\*/*italic\*/`code`/links go through a small line renderer (`_render_line`).

**The status footer** (`client/ui/status_bar.py`, one row under the input, provided by `chat_interface._footer` → `PinnedPromptReader(footer_text=…)`) shows `model · provider   ~/dir   ▓░░░░░░░ 90.1k · 9%` — what the NEXT turn costs, always in view. It **replaces the per-turn `[Context: N tokens]` print**, which reported the one number that mattered every turn and then scrolled away with the turn that printed it (and read as debug output). Three non-obvious constraints. (1) **The count must be cheap**, because the footer repaints at the app's `refresh_interval`: it prefers `agent._last_input_tokens` (the provider's exact number, free) and falls back to `client._count_context_tokens()` — a full walk of the history — only before the first turn of a session or right after a `--resume`/`/load`/`/branch` (which call `_forget_context_size`), memoized on `(len(messages), len(system_prompt))` so a repaint never re-walks. That fallback is the ~2×-over-counting estimator, so it is rendered with a leading `~`: a number that is permanently on screen has to say when it's a guess. (2) **It must never wrap** — a second row would push the input up on every repaint — so `status_bar.segments` drops whole groups (full path → `…/base` → no path → no provider) until the line fits, and the readout is padded flush RIGHT so the digits stay in one column instead of dancing as the count grows. (3) **`[Context: N]` still prints where nothing else shows it**: `client._print_context_size` is gated on `client.status_footer_active`, so the plain non-TTY loop, pipes and CI keep the line they always had. The flag is set in **`ChatInterface.__init__`** from `_dialog_is_tty()` rather than in `_run_pinned_loop`, because `main._resume_session` builds the ChatInterface and then restores the transcript BEFORE the loop starts — with a loop-time flag, a resumed session printed the line one row above the footer that already carried the same number. Thresholds are the compaction story, not decoration — amber at 70% and red at 90% of `conversation_manager.max_tokens`, with the high-water mark at 80% in between, so the bar turns amber BEFORE a compaction interrupts and red only once a turn is genuinely at risk.

**Notifying the user is a fifth display surface — the one that reaches them when the screen doesn't** (`client/ui/notify.py`). Everything else the UI does assumes someone is reading it; the two moments that can't assume that are a **long turn finishing** and a **prompt waiting for an answer**, both of which happen minutes after the user looked away. Two mechanisms, because neither is universal: the **bell** (`\a`), which every terminal has and which tmux/screen turn into a window-activity flag, and **OSC 9**, which iTerm2/WezTerm/kitty/Windows Terminal raise as a real desktop notification and other terminals discard. **Inside tmux or screen an OSC sequence must be wrapped in a DCS passthrough** (`_wrap_for_multiplexer`; tmux additionally requires every inner ESC to be DOUBLED) — without the wrap the notification is emitted perfectly and simply never arrives, which is the way this feature looks implemented and does nothing. Four suppression rules, because an unwanted notification is worse than none: nothing off a TTY (pipes, CI); nothing for a turn shorter than `NOTIFY.AFTER_SECONDS` (if you are still watching, a beep is an interruption); nothing for a turn **the user cancelled** (their hand is on the keyboard — hence the call sits beside the non-cancelled `_turn_end_line` print only); and a 10s minimum gap so a task confirming eight writes is one interruption. `notify_waiting` (from `tui._await_confirm`, the lifecycle shared by `confirm_ui`/`plan_approval_ui`, and from `question_ui` before the app comes down) is deliberately **not** duration-gated: a prompt holds the work until it is answered, whatever the turn's length so far. A background sub-agent finishing notifies from `notify_background_complete`'s idle branch — its delivery-only turn is seconds long, so the turn-end gate would silence exactly the case that matters. The raw escapes reach the terminal because the app runs under `patch_stdout(raw=True)`; a plain (non-raw) proxy would replace ESC with `?`.

**Four smaller display rules in the same family, each fixing something that read wrong.** A **tool call's name is colored** (`turn_view.render_tool_call`, the accent the file-op headers already used) — in white it was indistinguishable from the model's prose, so activity and answer blurred together. A **multi-step task renders as a checklist** (`turn_view.render_step_list`): `[✓]` for finished subtasks, **green `[ ]`** for the ones executing now, gray for pending — fed by `_run_subtasks_scheduled` from the single scheduling thread (`_run_subtask` runs on pool threads and would interleave), windowed to 8 rows with counted elision so a 30-step plan can't bury the answer it's working toward. It replaced a `[Step i/N: …]` line per subtask, which said nothing about what was done or what was left. **A printed block is frozen the moment it lands, so the plan lives in the pinned region instead** (`turn_view.StepStatus` → `tui`'s `steps_window`, wired as `agent.steps_sink` in `chat_interface._run_pinned_loop`): the scheduler marks steps running/done and the UI re-renders the SAME rows ~10×/second, so a plan is ONE block whose rows tick where the user is already looking. It is `stop()`ed in a `finally` (a cancel or a failed step must hand the region back, not leave a dead checklist pinned above the prompt for the rest of the session) and closed by one **all-checked block printed to scrollback** — the live block is transient, so that closing block is the plan's only permanent record. The **printed** shape survives as the off-TTY fallback, where there is no transient region (`agent._print_step_list` / `_print_step_done`, both scheduling-thread-only, spinner stopped first): a block per wave, printed BEFORE its steps run, plus a `[✓] 2/3 <step>` tick line as each one finishes (`tick = len(ready) > 1`; a lone step is skipped — the next block, or the closing one, marks it), consumed via `as_completed` so a tick belongs to the step that actually landed while the spinner label counts down (`_wave_label`). Those tick lines are what the live block replaced: in the common case — a decomposition whose subtasks are all independent, hence ONE wave — the user watched N green `[ ]` rows sit at `Steps 0/N` and then grow a separate `[✓] 1/N …` line per completion, instead of the rows in front of them being checked off. And a **resume is a marker line, not a bracketed dump** (`turn_view.render_session_notice` → `⟲ resumed <id>`, from `main._resume_session`), keeping the FULL session id because `--resume <id>` matches by suffix and the id has to stay copyable. Finally, a **finished turn prints a full stop** (`turn_view.render_turn_end` → `· done in 7m22s · 11:08`, via `chat_interface._turn_end_line`, `⊘ stopped after 12s · …` when cancelled), for every turn including a fast one — a streamed answer just STOPS, and the toolbar spinner that meant _working_ isn't scrollback, so afterwards nothing could say whether the turn had ended. Nothing announces a restored compaction any more: the notice that said how many messages a summary stood in for described an internal detail the user can't act on, above a transcript that had just replayed in full.

# CLAUDE.md

## Project Overview

Local agentic AI assistant built on LangGraph + MCP (Model Context Protocol). The client spawns an MCP server as a subprocess, routes queries through a StateGraph (classify → orchestrate/call_model ↔ execute_tools), and persists episodic memory, learned strategies (ACE Playbook), and user profiles across sessions. Supports Ollama, AWS Bedrock, OpenAI, Anthropic, SageMaker, and LiteLLM as LLM providers.

## Quick Commands

```bash
# Run from a checkout (src layout: package under src/, run as a module)
PYTHONPATH=src python -m mnemoai            # verbose (shows thinking)
PYTHONPATH=src python -m mnemoai --no-verbose

# Or install, then use the console command
uv tool install .        # or: pip install -e .
mnemoai

# Install dependencies (checkout dev)
pip install -r requirements.txt

# System-wide access (symlink once)
chmod +x bash/system-command-app/mnemoai-wrapper.sh
ln -sf $(pwd)/bash/system-command-app/mnemoai-wrapper.sh /usr/local/bin/mnemoai
```

## Architecture

```
main.py → ChatInterface → LangGraphClient.query()
  → inject episodic memory context
  → LangGraphAgent (StateGraph):
      classifier → [route] → call_model ↔ execute_tools (MCP)
                → [full]  → orchestrator → worker loops → aggregator
  → AgentConversationManager (summarize if over token limit)
  → UserProfileManager (learn preferences)
  → Reflector + PlaybookStore (learn from tool successes/failures)
```

**Client-server split:** The MCP server (`server/server.py`) runs as a stdio subprocess. The client maintains a persistent connection via a background asyncio thread in `client/mcp_tool_wrapper.py`. All tool calls route through MCP protocol.

### Config singleton (`utils/config.py`) ★

All configuration flows through `Config()` (`Config().get("SECTION.KEY", default)`); `utils/config.yaml` is gitignored. **Prompts are separate**: model-facing prompts live in **`prompts.yaml`** (accessed via `Config().prompt("KEY")`), never in `config.yaml`. `_load_prompts` layers the bundled package `prompts.yaml` under the user's file (user keys win, missing keys fall back), so a new prompt key reaches existing installs.

### MCP tool registration (`server/tools/tools_manager.py`)

`ToolManager.register_tools(mcp)` conditionally registers tool groups based on config toggles. Each tool file defines functions decorated with `@mcp.tool()`.

### Server-side safety policies (`server/tools/safety/`) ★

Two pure classifiers enforce, **inside the MCP server**, a hard floor that holds even if the server is driven directly. Narrow: they block only **catastrophic, irreversible** actions (root/home `rm -rf`, `mkfs`, raw-device `dd`, power-state changes, fork bomb; system-dir writes), NOT ordinary scoped mutations (those stay gated by the client `_confirm_tool` gate + plan mode). `bash_policy.classify_shell_command` (in `execute_bash` + `start_background_task`) and `path_policy.classify_write_path` (in `fs_write` + `file_edit`); config-independent, unit-tested.

### Blocking tools off the event loop (`server/tools/thread_offload.py`) ★

The server is ONE subprocess with ONE event loop and the SDK dispatches requests **concurrently**, so parallel agents really do have several tool calls in flight. A synchronous tool body never yields, so while it runs the loop can't dispatch, read, or even answer anything else — **one blocking tool freezes the tool layer for every agent** until the client's `MCP_CALL_TIMEOUT` kills their calls. `async def` does not help: it's the body that matters, and FastMCP runs a plain `def` inline too. **The convention, enforced at the single registration chokepoint by the `ThreadedToolServer` proxy (`ToolManager.register_tools`): nothing in `server/tools/` is `async def` unless it really awaits** — everything else is a plain `def` and `offload_blocking` runs it on a worker thread (`anyio.to_thread`, matching the SDK's backend). Hence `tool_error_handler` is sync-in/sync-out as well as async-in/async-out over one shared except-chain. Never pair `functools.wraps` with an explicit `__signature__` here (it would break FastMCP's schema generation). **The rule covers HELPERS, not just tools:** `fs_read` was `async def` awaiting readers that were themselves await-free `async def`s (one doing a blocking `model.invoke`), so the whole read chain ran on the loop — an `await` on a coroutine that never suspends buys nothing, only the leaf matters. `fs_read` and its readers are now plain `def`; `read_lines`/`read_json` count tokens incrementally (re-counting the accumulated text per line was quadratic: 9.8s for one 2839-line file vs 0.007s for a single count, so one read stalled every parallel agent for minutes); `process_large_content` fans chunks out on a `ThreadPoolExecutor`. **Two** AST scans in `tests/unit/test_thread_offload.py` fail on an await-free `async def` — one over `@mcp.tool()` functions, one over every `async def` in the package (the hole that let this survive).

### Read-before-write / staleness gate (`server/tools/read_state.py`) ★

A third server-side floor, distinct from the safety classifiers: an in-process registry that records the on-disk mtime of every file the model reads via `fs_read` (`record_read`), and blocks `fs_write`/`file_edit` from modifying an **existing** file that was never read or that **changed on disk since it was last read** (`check_write_allowed` → an `error`/`must_read_first`/`stale_read` payload). Creating a brand-new file is exempt; a successful write re-baselines the file (chained same-turn edits are fine). Keyed by `normcase(realpath(path))` so different spellings/case map to one entry. It never prompts (returns a normal tool error, so non-TTY / directly-driven servers can't deadlock) and is purely additive to the client `_confirm_tool` gate and the `path_policy` floor.

**A gate must never demand something that cannot be supplied — an EMPTY file is exempt.** The gate's precondition is a successful `fs_read`, and an empty file had none to give: `read_lines` resolved the full-file range to `1-0` and called it `Invalid line range`, an error, so `record_read` was skipped and every `fs_write`/`file_edit` on that file was refused with "read it first" — advice the model could follow forever without effect. A `touch`ed / `install`-stubbed file was therefore **unfillable** (observed: the model bounced between the two tools, then gave up and asked the user to delete the file or approve a shell workaround). Both halves are fixed: `read_lines` returns empty content with `total_lines: 0` (a read of nothing is a success — no request can be out of bounds when the file has no bounds), and `check_write_allowed` exempts a zero-byte file outright, which also covers the modes whose reader legitimately errors on it (`JSON` on an empty `.json`). The size check sits ABOVE the staleness check on purpose: a file emptied since the read has nothing left to protect. The exemption is sound because the gate protects CONTENT — an empty file has none, so it is a create in every way that matters. Note the sibling case that is still (deliberately) refused: an existing **binary** file can't be read as text, so text-writing over it stays blocked.

### Shell session state (`server/tools/shell_state.py`) ★

Two facts every shell tool needs and none should re-derive. **Which shell:** `subprocess(shell=True)` runs `/bin/sh` — dash on Debian/Ubuntu, POSIX-mode bash on macOS — so `[[ ]]`, arrays, `source`, process substitution break by host; the tools are documented as bash, so `bash_path()` feeds `executable=` (PATH first, then `/bin/bash`, else the default shell). **Where it runs:** each call is a fresh shell, so a `cd` used to evaporate and the next command silently worked in the wrong tree; `current_cwd()`/`set_cwd()` make the directory a command ENDS in the next one's start (probed out of band by `wrap_with_cwd_probe`, which preserves exit status and leaves stdout untouched). Process-wide (one shell session per server) and therefore **lock-guarded** — concurrent agents read/write it from many threads. A killed command doesn't move it; a deleted tracked dir falls back to the process cwd. Any new shell-spawning tool should use both (`execute_bash`, `start_background_task` do), and also pass `stdin=DEVNULL`: the server's stdin IS the MCP pipe.

### External MCP servers (`client/mcp_config.py`, `MultiMCPClient`) ★

Built-in server always launched; extra stdio servers declared in `~/.mnemoai/mcp/mcp.json` (`load_external_servers()`, tolerant). `MultiMCPClient` merges tools — a colliding external tool is namespaced `servername__tool` (built-in names win). External tools are appended to **every** route (incl. `simple_qa`) so routing never hides them, and injected into the decomposition prompt when orchestration is on. `/mcp` lists status.

### Hybrid search (semantic + BM25)

Used in both episodic memory and RAG. Pattern: get top-N candidates from vector store, get top-N from BM25, merge with configurable weights (`utils/bm25.py`).

### Multi-provider LLM abstraction (`models/controllers/llm_controller.py`) ★

`LangChainLLMController.initialize_model()` dispatches on `MODEL_ID.TYPE` (bedrock/mantle/ollama/openai/anthropic/sagemaker/litellm/mlx). Supported keys/kwarg mapping per provider live in `models/provider_params.py` (via `build_kwargs`); an `EXTRA_PARAMS` dict passes anything else verbatim into the request body. `anthropic` is the direct Anthropic API — distinct from Mantle's `anthropic` _protocol_ (Claude via Bedrock).

**Adding a provider means both tables plus the registry, or it's half-wired.** A `TYPE` must appear in the controller's `PROVIDERS` tuple, in `provider_params.py` for each section it serves, and have an `_initialize_<type>_model` / `_embed_<type>` method — declared-but-unregistered silently drops every param (`build_kwargs` finds no entry), registered-but-undeclared makes the configurator offer a `TYPE` that dispatch then rejects. `tests/unit/test_controller_dispatch.py` pins all three. Register a param in a provider's entry only if that provider's code path actually forwards it: `mlx` chat takes `TOP_K`, but `mlx` vision deliberately does not, because the server's multimodal handler never passes it to the sampler — config that looks effective and does nothing is worse than a missing knob.

**A provider request timeout is a hard requirement, not a tuning knob.** `TYPE: bedrock` MUST receive an explicit botocore `Config` (`_boto_config()`), because botocore's default `read_timeout` is only **60s** and it bounds the wait for the **FIRST response byte**, not idle time — on a large context the model spends that whole budget on prefill + reasoning before emitting anything (a ~440k-token turn at max effort measured ~123s to first byte), so every attempt times out. And since `read timed out` is classified transient, all retries then re-send the same oversized prompt and re-pay the same doomed wait — the turn can never complete. Keep `LLM.REQUEST_TIMEOUT` (default 600s) well above the largest expected time-to-first-byte, keep `CONNECT_TIMEOUT` short (connecting is fast; it must not inherit the request ceiling), and keep botocore's own retries **off** (`max_attempts: 0`) so this layer's retry/backoff isn't multiplied by boto's. `STREAM_IDLE_TIMEOUT` is a different guard — it only covers a stream that goes silent _after_ it has started.

**The Converse adapter fans in every Bedrock family, so ONE unhandled block type kills a whole family's turns** (`models/chat_models/bedrock_stream_compat.py`). `_parse_stream_event` builds each streamed block with `_bedrock_to_lc([payload])[0]` — an **unguarded index** into a list its own converter is free to return empty, and it returns empty for `reasoningContent.redactedContent` (branches exist for `.reasoningText` and `.text`, not the ENCRYPTED form). An OpenAI GPT model on Bedrock emits exactly that as the FIRST content block of every answer, so `openai.gpt-*` died on its first event with `IndexError: list index out of range` — before a word, on any prompt, and since the error is deterministic it was never retried. Streaming-only, hence unconditional here: the `disable_streaming` line above forces streaming ON, and a live probe that skips the app dodges the bug precisely because langchain-aws' hardcoded allowlist quietly disables streaming for a model id it doesn't recognize — so **verify a provider through the controller, not through a bare `ChatBedrockConverse`**, or the two paths disagree. `harden_converse_stream` wraps `model.client` (the transport) rather than subclassing, because the index lives in a module-level function `_stream` looks up directly and `_astream` just runs `_stream` in an executor. The predicate asks the library's own converter and treats only an EMPTY result as droppable — matching what the non-streamed path already does with that block — while a block it cannot classify still raises, so a new capability surfaces rather than vanishing. **The encrypted reasoning is unrecoverable, not merely unwired:** the payload is a KMS-wrapped `rsn_…` blob, and the provider returns no readable text at ANY `reasoning.effort` (`none`…`xhigh`) or `summary` setting — so these models never get a `Thought for Ns…` block, and that is provider policy, not a gap to fix. `REASONING_EFFORT` is still not mapped for them by design (see the non-Claude branch); `EXTRA_PARAMS: {additional_model_request_fields: {reasoning: {effort: high}}}` is the working knob — note `reasoning_effort` at that level is rejected as an unknown parameter.

**And because the predicate ASKS the library, the library's answer is a version, which a test must never bake in.** langchain-aws 1.7.4 (2026-08-26) added the `redactedContent` branch: the block now converts, the guard drops nothing, and the crash is gone upstream — while an install on 1.7.3 or older (the floor is `>=1.4.1`, and this machine was on 1.6.0, where the live failure was reproduced) still needs the guard to finish a turn. The first version of the tests asserted the 1.6.0 behavior as if it were the contract (`_is_parseable(redacted) is False`, and an unhardened stream RAISES), so they passed here and **failed in CI, which installs fresh** — the one environment that told us upstream had moved. Two rules follow. The guard's own contract is pinned against a **stub** converter (empty → drop, block → keep, raises → keep), so it holds on every version; the real-wire-shape cases either use a payload every version converts to nothing (an empty `reasoningContent`) or **skip on a probe of the installed library** (`_library_handles`) — including a forward test that on 1.7.4+ the block is KEPT, so "asks rather than remembers" is pinned in both directions. And event fixtures are **built per test, never shared**: `_extract_usage_metadata` does `response.pop("usage")` on the event dict, so one module-level list is emptied by the first consumer and the next test sees `{"metadata": {}}` → `KeyError` — a failure that looks like a bug in the code under test and is a leak between tests.

**The OpenAI-protocol adapter is LOSSY, and what it drops is the reasoning.** `ChatOpenAI` documents that it preserves no non-standard response field (only `tool_calls`/`function_call` reach `additional_kwargs`) — but every reasoning parser on a local server (MLX, llama-server, vLLM, SGLang, LM Studio) reports a thinking model's `<think>` block in exactly such a field, so the thinking was parsed, transmitted and thrown away one layer below the app: no `Thought for Ns…` block, while the same model on Ollama showed one. Turning the parser OFF is worse — the thinking then renders as answer prose, since `extract_content` only strips a stray `</think>`. `ChatOpenAIReasoning` (`models/chat_models/chat_openai_reasoning.py`) recovers it at the two adapter seams (`_convert_chunk_to_generation_chunk`, `_create_chat_result`) and normalizes to `additional_kwargs["reasoning_content"]`, the key `extract_content` already reads for Ollama/LiteLLM, so nothing downstream changes. **The field NAME is per-server AND per-parser, so hard-coding one is a silent gap:** `reasoning_content` (MLX/vLLM/llama-server/DeepSeek), `reasoning` (mlx_lm's own server, OpenRouter), a structured `reasoning_details`, `thinking`/`thinking_blocks` — first non-empty key wins and they are **never joined** (a provider commonly sends the same text under two names, so joining doubles the whole block), while blocks WITHIN one field do join. Wired into `_initialize_mlx_model`, `_initialize_openai_model` and `mantle_factory`'s OpenAI-shaped protocols; safe because it is purely additive (real OpenAI unaffected, inert on `responses`) and because `_convert_message_to_dict` never sends `additional_kwargs` back, so the recovered text can't reach a chat template that would reject it.

### Transient-failure retry (`client/agent/stream_policy.py`) ★

One home for "was this failure worth retrying, and how long do we wait" — used by the streamed turn AND by every non-streamed call. **A graceful fallback is what hides a missing retry:** route classification, task decomposition and the compaction summary each degrade cleanly (bind every tool / one `full` subtask / drop that batch), so on a provider overload (`529 overloaded_error`) they took the fallback on the FIRST rejection while the stream beside them recovered on attempt 2 — nothing crashed, the turn just got quietly dumber, and the compaction case lost that slice of history for good. All three now go through `call_with_transient_retry` / `acall_with_transient_retry` (`router._invoke_with_retry`, `agent._aux_invoke`, `agent_conversation_manager._with_transient_retry`): retry only `is_transient_network_error`, re-raise a deterministic error at once, and re-raise the last transient so the fallback still runs. Attempts cap at `AUX_RETRY_ATTEMPTS` (3) even when `LLM.MAX_RETRIES` is higher — with a working fallback a quick second chance beats a long stall, the opposite trade-off from the streamed turn. Backoff is **jittered** (`RETRY_JITTER`, applied after the 30s cap — waves/sub-agents/summary batches fan out together, so a deterministic delay makes them all re-collide) and defers to the provider's own `retry-after` when present (`retry_after_seconds`, httpx + botocore shapes, non-numeric ignored). The module stays logger-free and config-free: call sites read `LLM.*` and log via the shared `retry_notice` wording.

**Classification is by phrasing, so a provider that words a failure differently is a silent gap.** `TRANSIENT_NETWORK_MARKERS` had `connection closed`, but botocore's `ConnectionClosedError` reads "Connection **was** closed before we received a valid response…" — no substring match, so the single most retryable failure there is (a dropped `converse-stream` socket) was classified deterministic and retried **zero** times, surfacing as "an error I can't recover from automatically". Only `ReadTimeoutError`/`ConnectTimeoutError` matched at all (via `timeout`); five of botocore's seven transport errors were fatal. Its wordings are now matched explicitly. When adding a provider, check its exception `fmt` strings against the tuple rather than assuming the generic phrasings cover them.

**The same gap once more, in the SERVICE errors: a provider names them after its exception CLASS, and a class name has no spaces.** `ServiceUnavailableException` does not contain `service unavailable`, so Bedrock's "the model is busy, try again" — the failure a large-context Opus turn hits most — was deterministic: zero retries, and since botocore's own retries are off by design the message even says so (`reached max retries: 0`). `ThrottlingException` matched **nothing** in the tuple, so a 429 (transient by definition, and the one case where the provider often attaches its own `retry-after`) killed a turn outright. Observed as `! Router classification failed (…ServiceUnavailableException…); binding the full toolset` — a fallback taken on the FIRST rejection, exactly the shape the paragraph above is about: the streamed turn's own failure is louder, but the auxiliary calls degrade quietly. Both class-name forms are now matched, along with `too many requests` / `rate limit` / `429` and `ModelNotReadyException` (`model not found` must stay fatal — hence `model not ready`, not a looser `model not`).

**The first chunk is not covered by the idle watchdog** (`first_token_timeout`, `agent._stream_first_token_timeout`). `STREAM_IDLE_TIMEOUT` is for a stream that goes silent once RUNNING; the wait BEFORE the first chunk is prefill + reasoning over the whole prompt, which on a large context is minutes (~123s measured at ~440k tokens, and a 647k-token turn is ordinary once `MAX_CONVERSATION_TOKENS` is set for a 1M window). The watchdog policed that window too, so it aborted healthy turns at 120s and every retry re-paid the same doomed prefill — the turn could never complete, exactly the `read_timeout: 60` trap one layer up. The first-token window is derived from `LLM.REQUEST_TIMEOUT` + a 30s grace (so the provider's own, more specific timeout error wins a genuine overrun) and floored at the idle window — **derived, not a new config key**, so it reaches installs whose `config.yaml` will never mention it. It narrows back to `STREAM_IDLE_TIMEOUT` the moment data flows, and the two cases are distinguishable in the log (`No first token for Ns` vs `No stream data for Ns`).

**And a window that only holds "until the stream starts" is only as good as what counts as STARTED** (`stream_policy.chunk_has_payload`). An OpenAI-shaped server — a local MLX/llama-server/vLLM — primes the stream with a contentless `{"delta": {"role": "assistant"}}` the instant it ACCEPTS the request, before prefill has begun; the loop treated any chunk as the first token, so the whole widened window was handed back for the 120s per-chunk one while the model still hadn't produced a word. The paragraph above, undone by one empty dict: a large prompt aborted against a healthy server and every retry re-paid the same prefill (measured on MLX — priming chunk at +0.01s, first real token at +300s on a 43k-token prompt; 28 contentless chunks before the first token at +63s on a 6k one, so the flood is not hypothetical). Narrowing now requires **payload** — content, a tool-call fragment, reasoning in `additional_kwargs`, a finish reason, NON-ZERO usage (a priming chunk may carry an all-zero usage dict) — and an unclassifiable shape counts as a start, so an unknown provider never gets _slower_ dead-socket detection. Two consequences in `_iter_stream_with_idle_timeout`: the budget is a **wall-clock deadline, not a per-empty-poll accumulator** (only an EMPTY poll advanced the count, so keep-alives arriving faster than `_CANCEL_POLL_SECONDS` kept a dead turn open forever), and it is re-armed AFTER the `yield` returns, so the window covers the wait for the next chunk rather than the consumer's render time.

### Per-area models (`models/area_models.py`, `client._area_model`) ★

A turn is not one call: classification, decomposition and the compaction summary run beside the answer and are never shown, so `AREA_MODELS` gives each of the three (`ROUTER`/`ORCHESTRATOR`/`SUMMARY`) its own optional model. A value is a bare name or a **partial `MODEL_ID` merged over the main one and rebuilt through the ordinary provider dispatch** — hence an area may override `TYPE` (a different provider entirely) and `build_kwargs` still prunes params that provider doesn't take. `area_models` is pure config (tolerant: bare-string shorthand, any-case keys, empty values dropped, junk → no override); the build lives in `client._area_model` because it needs a live controller.

**A variant must re-apply the WHOLE param snapshot, not patch `model_id`.** `LangChainLLMController.__init__` snapshots every param into attributes and `initialize_model()` only dispatches on those, so `_apply_model_id()` is extracted and called by `build_model_variant(overrides, callbacks, non_reasoning)` on a fresh **peer** controller — the one path now used by the summary twin (`build_non_reasoning_model`), the sub-agent overrides (which previously hand-patched `model_id["NAME"]` + `model_name` and would have silently kept every other param stale) and the area models. **None means "use the main model", and is also what a failed build returns** (cached, so the failure is logged once, not per turn): an unreachable side model must degrade to a working turn. Wired in `client.start()` (ROUTER → `QueryRouter`, ORCHESTRATOR → `agent.orchestrator_model`, SUMMARY → `_summary_model`) and re-derived by `reload_inference_params` **after** clearing the caches, or the reload re-installs the pre-reload models. `router.usage_model_name` follows the override so `/usage` stays attributable, and `/doctor` lists the configured areas + any misspelled area name — the feature is otherwise indistinguishable from having no effect. `_decompose_task` keeps `base = self.orchestrator_model` **None-lazy** (`_non_reasoning` already resolves None to `self.model`) and only resolves it in the untwinnable branch, which mutates the model it actually invokes. The **aggregator is deliberately not an area**: its output is the user-visible answer.

**Settable from the app, and the two traps that makes** (`utils/configurator.py`): `_build_config` prompts for `ROUTER`/`ORCHESTRATOR` on first run when their toggle is on, and all three are rows in `_MODEL_SECTIONS`/`_PARAM_SECTIONS` so `/model` + `/params` reach them (drift-tested against `AREAS`; a row whose feature is off is shown tagged and `_area_gate` offers to enable it — hiding it would be indistinguishable from the feature not existing; `SUMMARY` is never gated). (1) **`section` was overloaded** — the registry tables know only `MODEL_ID`/`VISION_MODEL_ID`/`EMBED_MODEL_ID`, while an area's TEXT location is `ROUTER` under `AREA_MODELS:` and its CONTENTS are a partial `MODEL_ID`; one pure mapper (`_registry_section` → `"MODEL_ID"`) at every registry call site keeps both true with no signature change. (2) **"same as chat" means NO block, not a copy** — vision copies the chat block (`_copy_chat_to_vision`), but for an area absence IS the following behavior, so a copy would freeze today's model (`_clear_area_override`; answering yes writes nothing). Clearing must not use `_remove_top_section` (it absorbs the comment lines above the header — i.e. the commented example every template ships), so only the area's lines go and an emptied `AREA_MODELS:` header is dropped by hand; `_ensure_area_section` scaffolds below that comment block, takes its child indent from the existing body (mixed sibling indents are a YAML error) and expands the bare-name shorthand into a block so `/params` can tune it.

### Bedrock Mantle (`models/mantle_factory.py`) ★

`TYPE: mantle` reaches Bedrock Mantle via a bearer token minted from AWS creds. `API_PROTOCOL` picks the wire protocol: `chat_completions` (`/v1`), `responses` (`/openai/v1`), `anthropic` (`/anthropic`). Shared by LLM + vision controllers; availability varies by region.

### Prompt caching (`models/prompt_cache.py`) ★

A turn is many calls over a prefix that only grows, so it is marked with a cache breakpoint: later calls read it instead of re-paying, and the provider skips prefill it already did (the dominant part of time-to-first-byte). `policy(model_id)` → `CachePolicy`; `bind(model, policy)` attaches ONE `cache_control` kwarg that `langchain-aws` expands into Converse `cachePoint` blocks and `langchain-anthropic` forwards as the Messages-API breakpoint. **Provider-gated by necessity** (`CACHEABLE_TYPES` × `_CACHEABLE_FAMILIES`; `mantle` only on `API_PROTOCOL: anthropic`): an OpenAI-shaped endpoint 400s on the unknown kwarg. `system_message()` marks the system block on the **Anthropic transports only** — the per-turn injections ride the newest user message, so a tail-only marker matches nothing next turn (measured: 0 vs 4812 cached tokens read). Everything goes through the agent's two chokepoints, `_bind_tools` + `_system_message` (source-guarded by tests), and the bind lands only AFTER `bind_tools` — never on `agent.model`, which must stay a real model for `model_copy`. Config: `PROMPT_CACHE` (opt-out), `PROMPT_CACHE_TTL` (`5m`/`1h`), both `/params`-tunable since `rebind_model` re-reads the policy.

### Conversation compaction (`client/managers/agent_conversation_manager.py`) ★

Keeps history under `MAX_CONVERSATION_TOKENS` by summarizing older turns into the system prompt while keeping recent ones verbatim (auto over-budget, or `/compact`). The kept window is bounded by message count AND a token budget; the split point is tool-pair-safe (`_safe_tool_boundary`). **Layered context-overflow protection** (all auto-derive from the window): (1) cap each tool result at the source (`MAX_TOOL_RESULT_CHARS`); (2) pre-flight compaction — cheap tool-result eviction first (`evict_old_tool_results`, no model call), full LLM summary only if still over; (3) a 400 overflow backstop that compacts instead of re-looping. **The high-water trigger reads the provider's exact `input_tokens` (ground truth, = the footer's context meter) when a turn has run, not the ~2×-inflated estimate**, so it doesn't fire early. **Eviction runs first on EVERY compaction path** (manual/auto/backstop), not just the proactive check. The **summary uses a reasoning-disabled variant of the same model** (`llm_controller.build_non_reasoning_model`; provider-agnostic — thinking off, `verbose` off for Ollama; `LLM.SUMMARIZATION_THINK: true` keeps it on) and is a **parallel map + single reduce** (`generate_summary`: batches summarized concurrently under `SUBAGENT_MAX_CONCURRENCY`, then one reduce folds the ordered partials + any prior summary). Separately, **output-token truncation auto-continues** (`_continue_truncated_turn`, `MAX_OUTPUT_CONTINUE_RETRIES`) and a **stalled-stream watchdog** (`_iter_stream_with_idle_timeout`, `STREAM_IDLE_TIMEOUT`) re-runs a dead-socket turn on a fresh connection. See ARCHITECTURE.md for the full behavior of each.

**A mid-turn compaction cannot reach the turn that triggered it — the graph state is APPEND-ONLY.** `AgentState.messages` is `Annotated[…, operator.add]`, so a node can only add: compaction replaces `agent.messages`, but the running turn keeps re-reading the history `invoke()` seeded it with. The overflow backstop rebuilt only the RETRY prompt, so the next model call (after the next tool result) re-sent the pre-compaction prompt — and by then compaction had nothing left to give, so the turn dead-ended on "couldn't compact it further" over a history that was already tiny (observed: two overflows 2435 tokens apart, 3.15M vs a 1M window, the second right after a force-compaction to 2 messages). `invoke()` now records **`_turn_seed_len`** (where this turn's own messages begin) and the backstop stashes `_mid_turn_compaction = (compacted, seed)`; `_apply_mid_turn_compaction` substitutes it into EVERY later call of the turn — applied to the **raw** state list (only ever appended to, so the index still lines up) before `_sanitize_tool_pairs` can reorder anything, and keeping the turn's own tail so completed tool work survives the retry instead of being redone. **The same index fixes the mirror bug in `_commit_turn`**, which committed everything in the final state not already in `agent.messages`: after a compaction the summarized-away messages are no longer in that list, so all of them were appended BACK (undoing the compaction) and logged to the transcript as this turn's work. Live signature: `summarized 1209 older messages` followed one turn later by `1165 older messages` — the same history minus the 44 `HumanMessage`s that filter drops.

**A cached `input_tokens` must not outlive the history it measured** (`client._forget_context_size`, called from `resume_session` / `load_conversation` / `branch_conversation`). Since the trigger prefers the provider's exact count over the estimate, and a resume/`/load`/`/branch` REPLACES live history wholesale, the stale number describes a different conversation than the one now in memory: the high-water check passed and the first turn after a `/branch` went straight to a provider-side overflow (then, restoring re-inflated the whole pre-compaction transcript; since 1.12.6 a restore rebuilds the compacted state instead, but the count still measures the wrong history). `_compact` already nulls it; every path that REPLACES live history must too.

### Query routing (`client/agent/router.py`)

`QueryRouter.classify()` uses the LLM to categorize queries. Routes map to tool subsets in `ROUTE_TOOLS` — only relevant tools are bound per query.

### Orchestrator-workers (`client/agent/orchestrator.py`, `client/agent/agent.py`) ★

For "full" tasks: decompose → parse subtasks (JSON, with optional `depends_on`) → run a worker loop per subtask with category tools → aggregate. `_run_subtasks_scheduled` runs each dependency-satisfied **wave** concurrently on the bounded `ThreadPoolExecutor` (`LLM.SUBAGENT_MAX_CONCURRENCY`); no `depends_on` → sequential (backward-compatible). Parallel-wave workers run **headless** (`_headless_tl`) so an untrusted destructive tool auto-denies instead of stacking confirm prompts.

### Sub-agents (`spawn_agent`) (`client/agent/subagents.py`, `server/tools/subagent_tool.py`) ★

Model-initiated (distinct from the orchestrator): `spawn_agent(agent_type, prompt, description)` hands a task to a fresh sub-agent on its **own isolated context**, returning **only its final report**. Thin-stub + `_handle_spawn_agent` interception at both chokepoints; reuses `_run_worker_loop` in `quiet=True` mode (still streams via `_stream_once_quiet`, suppresses display). Built-in types `general-purpose`/`explore`/`plan` (+ custom `~/.mnemoai/agents/*.md`); no nested spawning; discovered via `available_subagents_block()`, no `/agents` command. Bounded parallel (`_run_spawn_batch`); **`run_in_background` defaults to true** (daemon thread + `BackgroundAgentRegistry`, auto-delivered when idle) — the model passes `false` only when it needs the report to continue the turn or a `general-purpose` sub-agent must edit un-approved things. `resume_agent` also defaults background (`load_from_disk` across restart). Background sub-agents run headless (auto-deny untrusted destructive tools). See ARCHITECTURE.md for the complete four-phase behavior.

### Session token accounting (`/usage`) (`client/usage_tracker.py`) ★

`UsageTracker` accumulates the providers' **reported** `usage_metadata` (input/output/cache) per model for the session, rendered by `usage_tracker.render` and surfaced as `/usage`. Fed from `agent._record_usage`, called by `_capture_input_tokens` (main loop), the **worker loop** (sub-agents + orchestrator waves), and `QueryRouter` (which takes an optional `usage=` sink — classification is a real call the user never sees). Thread-safe: parallel waves record from pool threads. **Two invariants:** (1) `_record_usage` is deliberately SEPARATE from `_last_input_tokens` — a quiet worker's prompt must count toward usage but must NOT set the main conversation's "current context size", or it corrupts the compaction trigger; (2) a call whose response carries no usage increments `calls_without_usage` instead of adding zeros, so a partial total can't look complete (the report calls itself a lower bound). **No USD, by design** — pricing isn't uniform across Ollama/SageMaker/LiteLLM, so a price table would be confidently wrong. Reset by `/clear`. **Cache writes read from three shapes** (`_cache_write`): normalized `cache_creation`, a nested per-TTL dict, else the per-TTL keys (`ephemeral_5m_input_tokens`/`ephemeral_1h_input_tokens`) — Bedrock and Mantle report thousands of written tokens there while leaving `cache_creation: 0`, which showed a caching session as "0 written", the one number that proves caching engaged.

### Context breakdown (`/context`) (`client/context_report.py`) ★

`/usage` is "what has this session spent"; `/context` is "what is my NEXT turn paying for, and which part can I shrink". Exists for the two costs nothing else surfaces: a large steering file (re-sent verbatim every turn, never reclaimable by compaction) and the tool schemas (bound on every call before a word of conversation). **Exact total, estimated split:** the total is the provider's reported `input_tokens` (the same ground truth the status footer shows) and each measured part is `scale`d onto it — unscaled, the estimator's ~2× over-count makes the parts sum to twice the number the user was just shown and reads as a bug (before any turn has run the report says it's estimating). The system prompt is broken up by **segmenting the live string** (`split_system_prompt`, marker-ordered with a moving cursor) rather than re-deriving each block, so it can't drift from what is actually sent (MEMORY.md edited mid-session, a compaction rebuild). Steering rows come from `SteeringStore.sizes()` — the size INJECTED, not on disk. `split_system_prompt`/`scale`/`render` are pure; `collect`/`report` take the client.

### Install self-check (`/doctor`) (`client/doctor.py`) ★

Every other report describes the conversation; this one describes the **machine** — because this app fails where the user can't see: the MCP server is a piped subprocess (a missing `rg` surfaces as one tool erroring mid-task), a feature toggle is a YAML line (`ENABLE_RAG: true` with no vector store looks like the model ignoring instructions), prompt caching is silently provider-gated (a config that _can't_ cache reads as one that does). Same split as `context_report`: `Check(section, name, status, detail, fix)` rows, pure `render`, `collect(client)`/`report(client)` take the client; `report` wraps everything in try/except so **a diagnostic that dies doesn't become the problem being diagnosed**. Checks the config/prompts file that actually **LOADED** (four resolution tiers, so "I edited config.yaml and nothing changed" is real — flags `$MNEMOAI_CONFIG` and a `(NOT <expected>)` mismatch), provider + credentials (never printing a key) + cache eligibility, `rg`/`git`/`bash`, **declared-vs-connected** external MCP servers (`mcp.json` vs `MultiMCPClient._members` — counting only what's live would call a FAILED server "not configured"), the optional dep behind each switched-ON feature, and the two per-turn files (`MEMORY.md` at ≥90% of cap → WARN, since the store trims silently; each steering file at its INJECTED size). **Local, cheap, read-only** — no LLM call, no write (running it must not change the state it reports); the one network op is a 2s TCP probe of a configured local provider.

### Workspace reports (`/files`, `/diff`, `/copy`) (`client/file_ledger.py`, `client/diff_report.py`, `client/ui/clipboard.py`) ★

Three commands about the **working tree**, not the conversation, all local (a report that costs a turn is a report nobody runs — none is a tool the model can call) and all following the `usage_tracker` split: pure `render`, client-taking `report(client)`. **`FileLedger` (`agent.files`, reset by `clear_context`) is the shared substrate**, fed from the ONE tool chokepoint (`tool_loop.run_tool_calls`, only after a SUCCESSFUL invoke) plus `@`-mention expansion — which is why it can account for work nobody watched (sub-agents, parallel waves) with no per-caller wiring. Narrow on purpose: only the three tools naming ONE file (`fs_read`/`fs_write`/`file_edit`), since a tree-wide `grep_search` yields no path to look at. Keyed `normcase(realpath())` (the read-before-write gate's key) so two spellings are one row; lock-guarded, non-raising, bounded with the excess COUNTED. **It is a ledger, not a context inventory** — a file whose result was evicted or summarized away stays listed, and the footer says so.

**`/diff` is `git status` plus the one column git can't produce**: which dirty file came from THIS conversation (`changed_paths()` → `mine`, sorted first, `✎` legended) — everything unmarked was already dirty, which is what decides what's safe to commit. **Read-only by construction, pinned by a test that regexes every `_git([...])` argv in the SOURCE** and allows only `rev-parse`/`diff`/`ls-files`. `diff --numstat HEAD` covers staged+unstaged at once; untracked come from `ls-files --others --exclude-standard`. Three parsing traps: a binary file's counts are `-`/`-`, a rename arrives as `old => new` or `dir/{old => new}/x`, and **an empty `git diff` is ambiguous** (unchanged-and-tracked vs never-seen — `_is_tracked` separates them, else every unchanged file renders as brand new). Bounded, and wherever output is cut the exact git command is printed.

**`/copy` exists because mouse selection copies the terminal's WRAPPING**, not the answer. Extraction is pure and separate from transport (`answer_text` matches `isinstance(AIMessage)` — an `AIMessageChunk` is a subclass; `last_code_block` keeps an unterminated fence, since the code is on screen). **The transport order is the design: over SSH, OSC 52 goes FIRST** — a local helper on the far end sets the clipboard of a machine nobody is sitting at. tmux/screen need the same DCS passthrough as OSC 9, hence `notify.wrap_for_multiplexer` is public rather than duplicated. An oversized payload is refused, not truncated. The module reads `sys` through itself: pytest's capture re-assigns `sys.stdout` at the start of the call phase and would undo a fixture-level patch.

### Diagnostics: one line on screen, the whole record on disk (`utils/logger.py`) ★

The terminal is a conversation, so **a stack trace must never render into it** — it buries the answer above it and asks the user to debug the app. `_ConsoleFormatter` (a `_ColorFormatter` subclass on the stderr handler) renders a record as **one line of the interface, not as a log line**: `✗ Query failed: division by zero`, the mark carrying the severity in the app's own vocabulary (`_LEVEL_MARKS`: `✗` red as in `console.print_error`, `!` amber / `·` dim as in `/doctor`) with the timestamp, logger name and level word left in the file — the console handler is attached only to `ai_app` (`propagate=False`), so nothing on screen needs to say where a record came from. The dim ` (traceback → ~/.mnemoai/logs/mnemoai.log)` tail is appended **only when something was dropped** (a traceback, or a message that didn't fit), else the pointer is noise. Length is capped at `_MAX_CONSOLE_CHARS` (500) through the shared `one_line()` — a provider error's message can carry a JSON body, which fills the window as effectively as the traceback we just moved out, and the same helper trims any UI text built from an exception so the two look alike. Outside verbose mode the record is **never passed through `Formatter.format` at all** (the line is assembled by hand): handlers run in order over the SAME object, so clearing `exc_info` in place — or letting `Formatter.format` cache `exc_text` — would strip the traceback from the file handler that runs next. `LOG_LEVEL=DEBUG` opts back into the full record + trace on screen.

**One failure, one report.** A `logger.error` beside a message the app already shows means the user reads about the same exception twice, so `extra={"console": False}` (honored by `_console_filter` on the console handler) keeps a record **file-only** — full traceback still on disk — and `log_file_hint()` gives the UI the same pointer to print. Used where the app's own wording IS the report: `client.query`'s turn failure (`✗ <ExcType>: <one line>` + a dim "conversation is intact" line) and `chat_interface`'s outer handler. The judgement is whether the visible text names the CAUSE: `agent._call_model`'s stream/model-failure branches keep their console line precisely because their prose is the turn's answer ("I lost the connection…") and can't say _which_ error, so the diagnostic adds the missing fact instead of repeating one.

**The leak was never our own `logger.error` calls — it was the ROOT logger.** `enable_file_logging()` attaches ONE `RotatingFileHandler` (`app_log_path()`, `delay=True`, 2 MB × 2 generations) to our logger (which has `propagate=False`, so a root handler would never see it) **and** to the root — where stdlib/third-party records land, and where a root with **no handler at all** falls back to `logging.lastResort`, which prints to stderr. That is how `concurrent.futures`' `Exception in worker` traceback appeared mid-chat: Esc cancels a turn by injecting `KeyboardInterrupt` into the worker thread (`tui._request_cancel`), a second Esc landed after the work returned but before `_worker`'s loop-thread `finally` cleared `_worker_tid`, so it hit the pool's own bookkeeping and the pool logged it CRITICAL. Both halves are fixed: `_dispatch_tracked` now clears the tid in its **own** `finally` (on the pool thread) inside a nested try, so a late injection is swallowed instead of escaping — and even if one escapes, the record has a home that isn't the screen. `threading.excepthook`/`sys.excepthook` are installed for the two paths that bypass logging entirely (`KeyboardInterrupt` exempt — a cancel is not a crash).

**`warnings.warn` is a fourth bypass, and the one the app can't fix at the call site.** `warnings.showwarning` prints its own four lines — path, line number, category, message, then the offending source line — directly to stderr, so `langchain_aws`' `RuntimeWarning: Tool messages were passed without toolConfig` landed mid-conversation as a raw block, twice per turn, right beside the one-line failures this whole section is about. `_install_warning_capture` (from `enable_file_logging`, idempotent) replaces the hook: the warning goes through `ai_app.warnings` — a CHILD of our logger, so it inherits both handlers while the file line still names its source — and reads as `! Tool messages were passed without toolConfig…` like any other warning. The origin (`RuntimeWarning from …/bedrock_converse.py:1270`) is appended to the FILE record only, by `_FileFormatter` reading `record.origin`; that is deliberately **not** treated as buried content (no ` (traceback → …)` pointer), because it's metadata in the same class as the timestamp and thread name the console already drops. A repeat is file-only via `extra={"console": False}` (`_seen_warnings`, keyed on origin+text and bounded — the stdlib's per-module registry doesn't survive a library that resets the filters, and the same warning twice reads as two problems). Deliberately NOT `logging.captureWarnings(True)`: that routes to `py.warnings` → the ROOT logger, which carries only the FILE handler here, so the warning would vanish from the screen entirely — and it logs the pre-formatted multi-line block as the message.

**Called from `main.cli()`, never at import time** (a unit test must not touch the real app home), idempotent, and best-effort — logging must not be the reason the app won't start. Our logger drops to INFO so the file gets lifecycle detail while the console keeps its own (higher) threshold; the root stays at `LOG_LEVEL` so third-party INFO chatter doesn't fill the file. Retention is age-based like sessions (`sweep_old_logs(LOG_MAX_AGE_DAYS)`, default 7, root-level config key, from `client.start()`) because rotation only bounds ONE noisy run; the sweep covers `mcp.log` too, and never creates `logs/` just to sweep it. `/doctor` reports the path, size and retention (`_log_check`), since the traceback behind a one-line error exists nowhere else.

### Branching, rewinding + exporting a conversation (`/branch`, `/rewind`, `/export`) ★

**`/branch [turn]`** (`session_log.branch_session` + `SessionLog.reopen` + `client.branch_conversation`) copies the transcript up to a turn into a NEW session, truncates live history to match, and re-points `agent.session_log` at the fork so this run keeps appending there. **The source file is never mutated** — that's the safety property (a dead-end branch costs nothing, so there's no confirm prompt). The copy is written as ONE `restore` record (the `seed_history` shape), so the fork's turn counter means "turns taken in the branch" and a fresh fork isn't offered as a picker duplicate. Two non-obvious requirements: the fork must be filed in the SOURCE's per-directory session dir (from `meta.cwd`, NOT the process cwd — else it vanishes from that project's picker), and `read_session`/`list_sessions` expose `branched_from` so the `--resume` row can be tagged `(branch @ turn N)` — a fork inherits its parent's opening prompt, so the rows are otherwise identical (the 1.8.1 indistinguishable-sessions bug class). `reopen()` skips `__init__` (no second `meta` record) and restores the turn counter from disk. Code snapshots are deliberately NOT implemented: a branch moves the conversation only, files on disk are untouched.

**`/rewind`** (`client/rewind.py`, `client.rewind_turn`) takes back the last prompt **and everything the turn produced** — the counterpart to `/compact` (which summarizes) and `/clear` (which throws the session away), neither of which undoes ONE thing. Truncates live history at `boundary()` (the last message that is a real typed prompt — every injection is a PREFIX on one, so what marks a turn start is that stripping them leaves something behind, the `turn_view.user_prompt_text` rule shared with the picker) and keeps the transcript in step. **It moves the conversation only; files on disk are never touched** — the boundary `/branch` draws, and why code snapshots stay out: a command that half-undid a turn would be worse than one that says which half it does. **It refuses rather than half-succeeds** — a compaction on or right after the withdrawn turn is unrewindable (the summary standing in for it can't be un-summarized), and the read-before-write gate + the `/files` ledger are deliberately left alone (both stay TRUE after a rewind: the file is still at that mtime, and "we looked at this" happened). What it can't reach is what the session LEARNED (episodic entry, playbook strategy, auto-extracted `MEMORY.md` fact — lossy by construction, so there's no entry to delete), so the notice NAMES those, and only the ones actually enabled. **Append-only means a withdrawal is a RECORD, not a deletion** (`SessionLog.log_rewind`, two shapes): a turn of this session goes by number (`{"n": …}`, and `_turn` is decremented so `_withdrawn_turns` matches newest-first), while an exchange that arrived inside a `restore` blob has no record to skip, so the surviving history is pinned instead (`{"messages": …}` — a **rebase**; without it the withdrawal would hold for this run and come back at the next `--resume`). The withdrawn text stays on disk. **A rewind narrows BOTH of `read_session`'s lists**, unlike a compaction: the by-number shape gets that for free by skipping the turn record, so the rebase shape must too, or the replay, the picker preview and `exchanges` would show text the restored state excludes. It also `_forget_context_size()`s and nulls `previous_query`/`_response`/`_messages`, else the delayed legacy episodic path stores the withdrawn exchange on the next prompt.

**`/export [md|txt] [path]`** (`client/transcript_export.py`, `client.export_transcript`) renders a **one-way human-readable** artifact — distinct from `/save`'s re-importable JSON — defaulting to the CWD, not the profile. Emits **no ANSI** (hence not reusing `turn_view.render_conversation`): tool _calls_ as one-line summaries with bulky args replaced by their size, tool **results dropped**, injected context stripped, reasoning opt-in. **Match message kinds with `isinstance`, never the class name** — a streamed reply is an `AIMessageChunk` (an `AIMessage` subclass), and an exact-name check silently exported a file of nothing but user prompts while every unit test passed. Same guard applied to `turn_view.render_conversation` (latent there: its callers only replay decoded history).

### Model-initiated questions (`ask_user_question`) (`client/agent/ask_user.py`, `server/tools/ask_user_question.py`) ★

`ask_user_question(question, options)` lets the model hand a decision back to the user instead of guessing. Thin stub + client-side intercept (`_handle_ask_user_question`) at both chokepoints — the same split as `exit_plan_mode` — driving `reader.question_ui`, which goes through `run_dialog` (a full-screen picker can't nest inside the running pinned app) and echoes the Q+A to scrollback from inside the dialog, the one window where a plain `print` is safe. **Every path returns a string, never blocks:** it is NOT bound into a sub-agent's toolset and refuses even if reached (`_spawn_depth`/`_is_headless`), because a background sub-agent has no terminal and a picker would park its daemon thread on a prompt that never paints; with no `_question_ui` hook (off-TTY/tests) it reports itself unavailable. A dismissal is a real answer — the model proceeds and states its assumption rather than re-asking. Validation is pure + unit-tested (2–8 distinct options; a malformed call never reaches the UI). Restores the spinner itself, since nothing else does on this client-side path.

### Agent collaborators (`client/agent/{message_codec,message_sanitizer,plan_policy,tool_formatting,confirmation_gate,tool_loop}.py`) ★

`LangGraphAgent` is the coordinator; its **stateless** logic lives in siblings it delegates to: `message_codec` (Strands↔LangChain), `message_sanitizer` (`sanitize_tool_pairs`), `plan_policy` (plan-block decision + read-only-bash heuristic + tables), `tool_formatting` (marker rendering, arg normalization, error translation). Thin `_…` methods on the agent delegate in, preserving the class surface the unit tests build against. Put new pure tool/plan/message logic in the collaborator, not `agent.py`.

**`message_codec`'s round trip MUST be idempotent — a resume decodes the whole transcript and re-encodes it, so any asymmetry compounds once per resume.** Decoding took `str()` of a tool result's `toolResult.content` **block list**, so the result came back as the literal `"[{'text': …}]"`; re-encoding wrapped THAT in a new block and re-escaped every quote in it, so each cycle roughly **doubled** the payload (measured: 31 chars → 4,735 after ten resumes; a real `fs_read` result reached **1.07M chars**, past `MAX_TOOL_RESULT_CHARS`, which is only applied once at the source — a live 1929-message transcript was 21M chars of which ~90% was backslashes, reported as `[Context: 12650351 tokens]`). `_tool_result_text` now READS the blocks (text joined, `json` blocks JSON-dumped) and `_tool_result_blocks` maps a list block-by-block instead of repr-ing it. `_collapse_wrapped_tool_result` repairs transcripts already on disk, unwrapping only an **exact** single-`text`-block literal (bounded by `_MAX_COLLAPSE_DEPTH`; nesting grows exponentially, so the bound is tested by lowering it, never by building 64 layers). Any new field added to either direction needs the same 50-cycle idempotence check (`tests/unit/test_message_codec.py`) — the failure is invisible per-turn and only surfaces after several resumes.

Two take the **agent as their first arg** (not pure — they call back into it, and dispatching through `agent._…` keeps a `__new__` test stub's overrides effective): `confirmation_gate` (the destructive-tool confirm gate) and **`tool_loop`** (`run_tool_calls` — the single model↔tool execution loop used by BOTH chokepoints, `_execute_tools` and `_run_worker_loop`, via `agent._run_tool_calls`). In `tool_loop`, **plan-mode blocking sits above the confirm gate** (a blocked tool must never prompt) and every branch answers through `_reply`, so each `tool_call_id` gets exactly one `ToolMessage` — an unanswered id makes the provider reject the next turn. `messages` is appended IN PLACE so a cancel leaves answered calls behind. Put anything about how a tool call is gated, invoked, or answered HERE, not in either caller: this replaced two hand-maintained copies that had already drifted (a fix for a bare `TimeoutError`'s empty `str()` reached only the foreground copy, so the worker logged a blank error for a release).

### Tool hooks (`client/hooks.py`, mounted in `client/agent/tool_loop.py`) ★

User-declared shell commands run around a tool call (`~/.mnemoai/hooks/hooks.json`, `/hooks`), for what a prompt can't enforce: format what gets written, refuse a path, auto-approve read-only commands, hint on failure. Events `PreToolUse`/`PostToolUse`/`PostToolUseFailure`, `matcher` globs the TOOL NAME, `type: command` only. **Gate order is the design — below the existing gates, never above:** safety floor → plan-mode block → `PreToolUse` hook → `_confirm_tool` → the tool. A `deny` is honored anywhere; an `allow` reaches exactly ONE gate (the confirmation prompt for that call) — it can't unblock plan mode or touch the server-side floors, because a config file must not widen what the app may do. Within an event, `deny` beats `allow` regardless of file order. Mounted ONCE (both chokepoints already share `tool_loop`): `agent._run_hooks` above the confirm gate + on both answer paths, `additionalContext` appended to the `ToolMessage` as `[Hook] …`, `_hook_deny_message` worded so a standing rule isn't retried as a transient failure. **App-home only and startup-snapshotted** — deliberately unlike steering: a `hooks.json` from a `git clone` would be RCE on the first edit, and hooks are code, so an edit mid-session must not change what's running (restart to apply; `active()` is lock-guarded because hooks fire from sub-agent/wave threads). **Never blocking, never interactive:** a crash, any non-`2` exit, or a `timeout` overrun is reported and skipped, and nothing can prompt (no terminal on those threads). Real bash (`bash_path()`); JSON on stdin (long `tool_input` values clipped, clipped keys named); `exit 2` denies with stderr as the reason; plain stdout is a user notice, never model context. No config toggle — presence is the switch, `hooks.json.example` is seeded/refreshed and the live file is NEVER created by seeding.

### ACE Playbook learning (`client/memory/reflector.py`, `client/memory/playbook_store.py`)

After each interaction, the Reflector analyzes tool trajectories, detects failure patterns, and extracts reusable strategies stored in the PlaybookStore. Relevant strategies are injected into the system prompt for future queries.

### Episodic memory (`client/memory/episodic_memory.py`)

Stores successful task completions with tool usage patterns. Retrieved via hybrid search before each query and injected as context.

### Session transcripts + `--resume` (`client/session_log.py`, `utils/paths.sessions_dir`) ★

**Automatic**, append-only per-directory transcripts that `mnemoai --resume` restores — the counterpart to the **user-curated** `/save`+`/load` (which stay untouched and are NEVER swept). One JSONL file per session under `{profile}/sessions/{sanitize_cwd(cwd)}/session_<ts>_<pid>_<rand>.jsonl`, so resuming in a project only offers that project's sessions. Record types: `meta` (session id, cwd, model), `turn` (the messages that turn added), `compact` (a restorable checkpoint — see below), `restore`, `label`. CLI: `--resume` (picker, newest-first, listing capped at 20), `--resume <id>`, `--continue` (most recent, non-interactive) — all handled in `main._resume_session` → `client.resume_session`, which reuses the SAME decode+replay path as `/load`. Expiry is **age-based only** (`SESSION_MAX_AGE_DAYS`, default 30, root-level config key; `0` disables recording entirely) and sweeps EVERY project dir at startup — the picker cap limits what's _offered_, never what's kept, so a cap can't silently drop a session.

**The picker lists one row per CONVERSATION, not per file** (`list_sessions`): resuming writes a NEW file seeded with the whole prior conversation, so a chat resumed 3× exists as 4 files — each a strict SUPERSET of the last, sharing one opening prompt. A session that another session `resumed_from` is therefore SUPPRESSED (its content is entirely inside its successor); a `/branch` fork is NOT (it diverges rather than supersedes, so both are real). Rows are sized by `exchanges` — real user prompts across the WHOLE restorable conversation — because `turns` counts only turns taken in that file, which made a resumed 243-message chat display as "1 turn" and read as the shortest entry. An **explicit `--resume <id>` resolves against `collapse_chains=False`**, so collapsing a row from the menu never makes that point unreachable.

**Five invariants** (full detail in ARCHITECTURE.md): (1) **append-only, NOT a mirror of `agent.messages`** — compaction replaces that list wholesale, so the turn is buffered in `invoke()` and flushed once via `_log_turn`, never index-sliced; (2) **sub-agents are NOT logged** (isolated `worker_messages`, never in `_messages`); (3) **a cancelled turn IS logged** with its interrupted marker, every write is best-effort, and `resume_session` deliberately does NOT set `current_conversation_path` so a bare `/save` after a resume can't overwrite a saved conversation; (4) **the transcript must never diverge from live history** — a turn killed by ANY mid-flight exception (dropped provider connection, MCP error) is logged before the `raise`, because its work stays in `_messages` and the user keeps talking: without that the log silently stopped at the last SUCCESSFUL turn while the chat ran on for another hour (observed: 64 of 408 messages recorded, invisible because `_log_turn` swallows errors); (5) **a restored conversation is SEEDED into the new session file** (`seed_history` → a `restore` record, from both `resume_session` and `load_conversation`), so each file is self-contained and a resume-of-a-resume doesn't truncate the chain — the source file is never mutated, and a `restore` record does NOT count toward `turns` (so it can't inflate the picker's count, and an unused resume still qualifies as empty for `discard_if_empty`).

**A restore must reproduce the COMPACTED state, not the raw history — append-only is about the FILE, not about what comes back.** A `compact` record is a **checkpoint**: `messages` (the history that stayed live) plus, when older turns were summarized away, `summary` — written by `_compact` via `log_compaction(summary=…, kept=…)`. `read_session` therefore returns two lists — **`messages`** (what to RESTORE: a checkpoint rewinds it to the kept window) and **`all_messages`** (everything ever logged and not withdrawn by a `/rewind`, what the replay + picker preview + `exchanges` read) — plus `summary`, `compacted_away` and `checkpoint`. Without it every resume silently UNDID the compaction: the live context jumped back to the raw pre-compaction history (measured: 235,793 tokens on screen → 1,166,221 after `--resume`, past the window), so the first turn back re-summarized the whole chat and the summary already paid for was discarded. All three restore paths carry it (`resume_session`, `load_conversation`, `branch_conversation`) — each rehydrates `messages` and then calls `conversation_manager.apply_restored_summary`, which rebuilds the prompt through the SAME `_build_system_with_summary` a live compaction uses (so the session blocks come back and `previous_summary` is set, without which the next compaction's reduce step drops this history). `seed_history(…, summary=…, kept=…)` re-states the checkpoint in the new file so a resume-of-a-resume doesn't re-inflate; `branch_session` copies a checkpoint only when the branch point is AFTER it. **Three coupled consequences:** the manager keeps `summary_text` (the RAW text) beside `previous_summary` (the wrapped `<conversation_summary>` block) because `/save` persists the former and `/load` re-wraps it — persisting the wrapped form would nest a block in a block; `list_sessions` judges emptiness on `all_messages` (a checkpoint can leave `messages` empty in a very real conversation) and previews from it too (the kept window no longer holds the opening prompt); and `/clear` must null BOTH copies, or a cleared conversation's history reaches the next summary and the next `/save`. A record with NEITHER key (pre-1.12.6, or the fallback when the kept window can't be encoded) keeps its old purely-informational meaning — it restores everything, which is safe.

**What marks a record as restorable is `messages`, NOT `summary` — the context shrinks two ways.** A summary replaces older turns; **tool-result eviction** (the cheap no-model-call layer that runs first on every compaction path) drops no message at all — it rewrites old results smaller — so there is no summary to record, yet the resulting state is just as unreachable from the raw turns, which hold every result at its ORIGINAL size. Eviction that brought the estimate back under budget therefore returned without logging anything, and the next resume replayed the full-size results and handed back exactly the tokens eviction had reclaimed — the same defect a summary checkpoint fixed one release earlier. `client._log_eviction_checkpoint` (from `_compact_now`'s eviction-only branch, and deliberately NOT when it falls through to the summary, which writes its own — a second record there would duplicate the whole history for nothing) writes `log_compaction(kept=…)` with no summary; it is best-effort, since by then the context IS smaller and raising would turn a successful compaction into a failed turn. Two consequences: an eviction record must **not clear** a summary an earlier compaction left standing (`read_session`/`branch_session` update `summary` only `if "summary" in rec`), and because eviction drops no message `compacted_away` is 0 for it — so `read_session` also returns **`checkpoint: bool`**, as neither `summary` nor `compacted_away` can tell a caller that `messages` is narrower than `all_messages`. Every caller passes `kept=` to `seed_history` **only when there is a checkpoint**, else the whole conversation is duplicated into the new file.

**A file whose records PIN a narrower state must survive both filters that assume a file is only worth keeping for its turns** (`SessionLog._pinned_state`, set by `log_compaction` and by a `/rewind` rebase). Such a file holds state that exists nowhere else — the compaction/withdrawal happened HERE, while the parent still holds the full history — so `discard_if_empty` keeps it even with zero turns (before this, a resume → `/compact` → quit-without-a-turn unlinked the file and the next resume re-inflated the whole pre-compaction history), and `list_sessions` exempts a `checkpoint` file from its `all_messages`-empty AND `turns == 0` tests (else the picker offered the PARENT — the one file still carrying the exchange the user just withdrew). A checkpoint merely RE-STATED by `seed_history` doesn't count (`log_compaction(seeded=True)`): the parent owns that state, so an unused resume file must stay discardable.

**Anything a person reads back shows what the USER typed** — one shared stripper, `turn_view.user_prompt_text`, removes the prepended `[Episodic Memory …]` block, the ephemeral `<steering>`/`<plan-mode-active>` reminders, and auto-delivered background sub-agent reports. Used by the **replay** (`render_conversation`), the `--resume` **picker label** (`first_user_prompt`), and **`/export`**. It lived as three separate copies and the replay never had it, so every resume opened with a ~30-line dump of episodic tool names and the first prompt lost its `>` marker. `session_log.first_user_prompt` (shared by the `--resume` picker AND `client.conversation_title` for `/load`) strips every injected prefix: the ephemeral `<steering>`/`<plan-mode-active>` blocks, the prepended `[Episodic Memory …]` block, tool-result-only messages, and auto-delivered background sub-agent reports, falling through to the next user message when one yields nothing. Unstripped, every row read `[Episodic Memory …] 1. "hello" → …` and unrelated sessions were indistinguishable.

**`/rename [title]` names a session** (`SessionLog.set_label` → a `label` record; `client.rename_session`/`session_label`), because the picker otherwise labels every row with its first prompt — the one thing a resumed conversation and its parent share. Append-only like everything else, so **last one wins** and an empty title clears it; a `label` is **NOT a turn** (it can't make a turn-less session resumable, nor save its file from `discard_if_empty`). `list_sessions` carries it and `main._format_session_label` prefers it over the preview, keeping the `(branch @ turn N)`/`(continued)` tag. **It survives a resume but deliberately not a `/branch`:** `_seed_session_log(…, label=…)` re-stamps it (a resume continues the SAME conversation), while `branch_session` copies only `turn`/`restore` records — a fork already inherits the opening prompt, so inheriting the name too recreates the indistinguishable-rows bug.

**Tests that drive a real client MUST isolate `$MNEMOAI_HOME`** (`tests/integration/conftest.py::_isolated_app_home`, pinning `$MNEMOAI_CONFIG`/`$MNEMOAI_PROMPTS` to the already-resolved real files so the tier still runs against the configured provider). The integration tier builds a REAL `LangGraphClient`, so without this every run wrote test transcripts into the developer's own app home — they then showed up in `--resume` as fake conversations full of `"Hello"` / `"What is the capital of France?"` — plus episodic/playbook entries learned from test prompts.

**Three UX rules** (each was a bug): `_resume_session` returns **`"exit"`/`"resumed"`/`"fresh"`**, not a bool — cancelling the picker EXITS instead of falling through to a fresh chat, and `"fresh"` (no sessions yet) must not be conflated with `"resumed"`; the **banner prints before the transcript** (`show_welcome()` from `_resume_session`, `run_chat_loop(welcome=False)`) so the conversation lands above the prompt, not above the logo; and **turn-less session files are unlinked at exit** (`discard_if_empty`, verified zero-turn first) since `meta` is written before we know the user will type anything.

### Curated memory (MEMORY.md) (`client/memory/memory_store.py`, `server/tools/memory_tool.py`) ★

A small, bounded, profile-scoped `~/.mnemoai/{profile}/MEMORY.md` of durable facts the agent **curates itself** via the MCP `memory` tool (`add`/`replace`/`remove`; entries `---`-separated). Injected **whole** into the system prompt at session start (frozen snapshot). Hard char cap (`MEMORY.MAX_CHARS`, default 2200) forces consolidation. Entries tagged `[user]`/`[feedback]`/`[project]`/`[reference]`. Gated by `ENABLE_MEMORY`; writes confirmation-gated by `REQUIRE_MEMORY_CONFIRMATION` (default false). **Auto-extraction** (opt-in `ENABLE_MEMORY_AUTO_EXTRACTION`) distills facts at turn end on a daemon thread, writing without a prompt. Distinct from episodic memory + the playbook.

### Steering (STEERING.md / CLAUDE.md) (`client/memory/steering_store.py`, `utils/paths.steering_files`) ★

**User-authored, always-on instructions** — the read-only counterpart to `MEMORY.md`. Discovered hierarchically (the app home + every dir from the CWD up to the repo root, or below `$HOME` when there is no repo), concatenated broadest→specific. Injected as a leading `<steering>` block **every turn** by `client._steering_reminder()`, then **stripped before storage** by `_strip_ephemeral` — so it's re-read from disk each turn (edits apply immediately) and never summarized by compaction (always verbatim). No config toggle (presence is the switch), no slash command.

**Two accepted filenames** (`paths.STEERING_FILENAMES`, applied per directory by `instruction_file_in`): `STEERING.md`, else `CLAUDE.md`, so a repo that already keeps agent instructions under that name needs no second file. Each directory contributes **at most one** file (a sibling `CLAUDE.md` is shadowed, not concatenated), and **the shadowing is per-directory, NEVER global** — a project `STEERING.md` must not switch a global `CLAUDE.md` off, which is the one invariant to preserve here (both directions are unit-tested; a global-shadowing version passes the obvious test and fails the reverse one). Reading accepts both names but the **write** target stays `STEERING.md` (`global_steering_path`), and de-dup keys on `normcase(realpath(...))` since `app_home()` is unresolved while the walk resolves. Nothing outside the app home is read for the global tier — a file another tool owns must not silently become the always-on instructions. **The unrooted walk stops below `Path.home()`** (`_walk_boundary_dirs`): with no `.git` in any ancestor it used to reach `/`, so one `~/CLAUDE.md` became always-on for every non-repo directory under it — the same "another tool's file must not become global" rule, in the tier where it's easy to miss. An explicit `.git` AT `$HOME` (a dotfiles repo) is still an ordinary project root, so both directions are unit-tested. **The content is paid EVERY turn** and compaction can never reclaim it (it's stripped before storage), so each file is capped at `STEERING.MAX_CHARS` (`steering_store._DEFAULT_MAX_CHARS`, 45000) with a visible truncation note — a large repo `CLAUDE.md` (this repo's own is ~55KB ≈ 14k tokens) is a real per-turn cost, not a one-off. The code default and all three `config.yaml*.example` values are pinned equal by a test, since the examples are what users read.

**`@path` includes** (`references` + `resolve_reference` + `_included_blocks`): a file may pull in another, so a long ruleset splits into focused files. Resolved against the **referencing file's** dir (not the process cwd), `~` expands; a reference that isn't a readable file resolves to None and is simply left in the prose — which is what makes `@staticmethod`, an `@handle`, or an email harmless, and why the regex requires line-start/whitespace/bracket before the `@`. Breadth-first and bounded three ways because this is per-turn cost compaction can't reclaim: depth 3, 20 files, and the **remaining share of the source file's own `STEERING.MAX_CHARS`** (so splitting can't sidestep the cap); anything omitted says so in the block. `sizes()` exposes per-file injected sizes to `/context`.

### Agent Skills (`client/memory/skill_store.py`, `server/tools/skill_tool.py`) ★

Authored, on-demand instruction packs, one per dir: `~/.mnemoai/skills/{name}/SKILL.md` (frontmatter `name`+`description`, optional `argument_hint`, markdown body). **Three-tier progressive disclosure**: (1) name+description injected at session start (`<available_skills>`, size-bounded); (2) full body loaded only when the model calls `use_skill` (return value _is_ the body); (3) bundled resources read on demand. Directory name is the id. `SkillStore` is tolerant pure file logic shared by the server tool + client injection + `/skills`. `use_skill` is always-available. Gated by `ENABLE_SKILLS`; bundled example seeded on first run.

### User-defined slash commands (`client/user_commands.py`) ★

Prompt macros the USER types: one `~/.mnemoai/commands/<name>.md` per command (file stem = the token), optional frontmatter (`description`, `argument_hint`) + a markdown body that becomes the prompt, with `$ARGUMENTS` / `$1`…`$9` substituted in ONE regex pass (a substituted value is never re-scanned; `$12` is left alone). **A body with no placeholder gets the arguments appended** — the common case is an instruction plus a target, and silently dropping what was typed reads as a bug. Expansion is client-side in `chat_interface._dispatch`, **after every built-in** (so a file can never shadow one — a colliding file is rejected with a reason, since the dispatcher would never reach it) and **before** the empty-line branch; a non-matching `/thing` returns None and still goes to the model as prose. The model never learns a command ran (the expansion IS the prompt), so one dim `turn_view.render_command_expansion` line is the only record that the turn's question came from a file. **Presence is the switch** (no toggle) and **app-home only**, like `agents/`/`skills/` and deliberately unlike per-project steering: a `git clone` must not redefine what a name the user types expands to. Tolerant memoized scan (`_dir_signature`, so an edit applies to the next typed line without re-parsing per keystroke); rejects surface via `print_error` AND `/doctor` (`doctor._command_checks`). `BUILTIN_COMMANDS` lives HERE, not in the UI, so pure file logic can answer "is this name taken" (a test pins it ⊇ `ChatInterface._COMMANDS`). **A user row must never widen the command box** (`_user_command_group`): both columns are padded to their widest member and the frame grows to its longest row, so labels/descriptions are clipped to the built-ins' widths, the `argument_hint` moves into the `/` menu's meta text, and 6 rows cap the group with a `… +N more` line.

### `@`-file mentions (`client/file_mentions.py`) ★

The user pointing at a file: `@path` typed anywhere in a line **completes as you type** and, on submit, is **read and attached** to the prompt — so the content is there whether or not the model would have gone looking. Pure file logic (no MCP, no LLM, no prompt*toolkit), so the completer and the dispatcher share one definition of what matches and what attaches. **The syntax is steering's** — `expand()` scans with `steering_store.references()` rather than a second regex, which is also what keeps `@staticmethod` / `@handle` / an email harmless (a ref that doesn't resolve to a readable path is simply left in the prose; only one that \_looks* like a path — has a `/` or a dot — earns a gray `no such file`). Local `resolve()` differs from steering's on the two real points: relative refs are anchored to the **prompt's cwd** (a steering ref belongs to the file that wrote it), and a **directory** resolves too, contributing its bounded listing instead of its files. **Inlining is bounded three ways** because it lands in the USER's message: compaction can summarize it, tool-result eviction can never shrink it — `_MAX_FILES` (10), `_MAX_TOTAL_CHARS` (60k) and per-file `MENTIONS.MAX_FILE_CHARS` (code default 20 000, `0` disables — read like `STEERING.MAX_CHARS`, so no config edit is needed to reach existing installs), each overrun reported in the `Mention` and, for a truncation, stated in the prompt so the model doesn't read the cut as "nothing there". **A mention is NOT a read:** `server/tools/read_state.py` still demands its own `fs_read` before an edit. Two completion modes (`completions()`): a fragment with a `/` or starting `~`/`\` completes its **last segment** from the parent dir (`os.scandir`, so it reaches outside the project), a bare fragment matches the **project index by basename** (`@chat_int` → `src/mnemoai/client/ui/chat_interface.py`) — `git ls-files` (2s, honors `.gitignore`), else a bounded `os.walk`, TTL-cached 10s per dir in a process-global `_INDEX_CACHE` so a keystroke burst costs one scan. **Every entry point is non-raising**, since a completer that throws takes the pinned input down with it and a mention is typed mid-sentence by someone who wants an answer. UI side: `tui.FileMentionCompleter` joined to `SlashCommandCompleter` via `merge_completers` (only one can match a cursor position, so they never compete for the popup) with `start_position=-len(fragment)`; `chat_interface._expand_mentions` runs in `_dispatch` **after** the user-command expansion (a command body can mention files) and after every built-in (`/save @notes.md` keeps its literal argument), printing one `turn_view.render_mention_notice` line per mention — attaching nothing and attaching the right file read identically otherwise.

### Terminal UI (`client/ui/chat_interface.py`, `client/ui/tui.py`, `client/ui/turn_view.py`, `client/ui/status_bar.py`, `client/ui/notify.py`, `client/ui/screen.py`) ★

Pinned-input REPL on a TTY (`PinnedPromptReader`): a non-full-screen prompt*toolkit `Application` keeps `>` at the bottom while output streams above via `patch_stdout(raw=True)` (scrollback/copy-paste preserved). Query runs on a worker thread (`client.query()` calls `asyncio.run()` internally). `Ctrl+J` newline / Enter submit; Esc/Ctrl+C cancels a turn; **a message submitted mid-turn is QUEUED FIFO and runs as its own turn after the current one ends** (shown as a dim `> … (queued)` line, never concurrent, never folded into the running turn). The agent-side mid-turn \_steering* machinery (`agent.steer`/`_drain_steering`, drained in `_execute_tools`/`_orchestrate`) still exists but is **not** fed by the UI — it was retired as the default because a message steered during the final tool-call-free model call was never drained at turn end and leaked into the next turn. (Distinct from background sub-agent auto-delivery, which uses its own `drain_background_completions`, not the steer queue.) Styled turn view: collapsed "Thought for Ns…" blocks + `ToolName`/`↳ arg` blocks; loaded conversations replay through the **same** `CodeFormatter` (`turn_view.render_markdown`) so reloaded answers render identically. Confirmations + dialog commands (`/load`, `/config`, …) run via in-app hooks; degrades to a plain `input()` loop off-TTY. **Settings commands split deliberately:** `/config`, `/model`, `/features` re-exec (`_restart_in_place`) because they can change the provider/model or a toggle that gates MCP tool registration at subprocess boot — and since `os.execv` REPLACES the process (no `atexit`, no `finally`), that method must discard a turn-less session file itself or the restart leaks one; `/params` touches inference knobs only, so it reloads in place via `client.reload_inference_params()` and KEEPS the conversation (a restart there discarded the chat, worst right after a `--resume`, where the restored history lived only in the file the restart abandoned). Reloading needs a FRESH `LangChainLLMController` (it snapshots params at construction) and every model holder re-pointed via `agent.rebind_model` + `router.model` + dropping the summary/sub-agent caches, else the change half-applies. Streamed answers render through `CodeFormatter` (markdown-it-py re-parse-per-chunk + Pygments). **The command reference is `/help` ONLY, and the launch banner deliberately doesn't print it** (`_command_box` over `_COMMAND_GROUPS`, plus the keys that aren't commands — Esc to interrupt, `Ctrl+J`, `Ctrl+A` — which nothing else surfaces). The banner printed the same box and was **41 lines: a full screen of chrome before the first prompt**, for a list that `/help` and the `/` menu each put one keystroke away — the box's own last row said exactly that, which is the tell that the launch copy was redundant. What's left (`__welcome_message`, ~10 lines) answers only what a launch must: wordmark, tagline, **version** (via `app_version()` in `mnemoai/__init__.py`, shared with `/doctor`; the one fact the pinned footer doesn't carry — and EMPTY, not a placeholder, from a checkout with no install metadata), and one line naming the three ways in (`/help`, `/`, `@`). Flush left, since with the box gone there's nothing to center over. A new command belongs in `_COMMAND_GROUPS` **and** `_COMMANDS` (the `/` autocomplete) — the two-list drift tests read `_COMMAND_GROUPS` directly, so they still hold with the box off the launch path. A file edit renders as a **line-level** diff (`turn_view._diff_lines`, `difflib` opcodes): only changed lines are colored, unchanged neighbours stay gray context, long unchanged runs elide to `… N unchanged lines`. See ARCHITECTURE.md for the full behavior.

**The status footer (`client/ui/status_bar.py`) replaces the per-turn `[Context: N tokens]` print** — that number matters every turn but scrolled away with the turn that printed it. One pinned row under the input (`chat_interface._footer` → `PinnedPromptReader(footer_text=…)`): `model · provider   ~/dir   ▓░░░░░░░ 90.1k · 9%`, amber ≥70% / red ≥90% of `conversation_manager.max_tokens` (the high-water mark sits at 80% in between, so it warns BEFORE a compaction interrupts). Three constraints. **Cheap:** it repaints at the app's `refresh_interval`, so it prefers `agent._last_input_tokens` (free, exact) and falls back to `_count_context_tokens()` — a full history walk — only before the first turn or right after a `--resume`/`/load`/`/branch` (which `_forget_context_size`), memoized on `(len(messages), len(system_prompt))`; that fallback is the ~2×-over-counting estimator, so it renders with a leading `~` (a permanent number must say when it's a guess). **Never wraps:** the window is one row, so `segments` drops whole groups (full path → `…/base` → no path → no provider) until it fits, and the readout is flush RIGHT so the digits don't dance as the count grows. **The old line survives where nothing else shows it:** `client._print_context_size` is gated on `client.status_footer_active`, keeping it for the plain off-TTY loop, pipes and CI. That flag is set in **`ChatInterface.__init__`** from `_dialog_is_tty()`, NOT in `_run_pinned_loop` — `--resume` restores from `main._resume_session` (which builds the ChatInterface first) BEFORE the loop starts, so a loop-time flag left the resumed session printing the line right above the footer that already showed it. `status_bar` is pure (no prompt_toolkit, no I/O) and the provider call is try/except-wrapped, so a footer error can't take the UI down.

**Notifying the user (`client/ui/notify.py`) is the surface that reaches them when the screen doesn't.** Two moments can't assume anyone is reading: a **long turn finishing** and a **prompt waiting for an answer**. Two mechanisms, since neither is universal — the **bell** (`\a`, every terminal, becomes a tmux/screen activity flag) and **OSC 9** (a real desktop notification on iTerm2/WezTerm/kitty/Windows Terminal, discarded elsewhere). **Inside tmux/screen the OSC half MUST be wrapped in a DCS passthrough** (`_wrap_for_multiplexer`, tmux also needs every inner ESC DOUBLED): without it the sequence is emitted perfectly and never arrives — the way this feature looks implemented and does nothing. Four suppression rules (an unwanted notification is worse than none): TTY only; nothing under `NOTIFY.AFTER_SECONDS` (default 30, code default so no config edit is needed, `0` = never); nothing for a turn the **user cancelled** (hence the call sits only beside the non-cancelled `_turn_end_line` print in `chat_interface._dispatch`); and a 10s min gap so a task confirming eight writes is ONE interruption. `notify_waiting` (`tui._await_confirm` — the lifecycle behind `confirm_ui`/`plan_approval_ui` — and `question_ui`) is deliberately **not** duration-gated: a prompt holds the work regardless of how long the turn has run. A background sub-agent notifies from `notify_background_complete`'s idle branch, because its delivery-only turn is seconds long and the turn-end gate would silence exactly the case that matters. Raw escapes reach the terminal only because the app runs under `patch_stdout(raw=True)`.

**A launch starts on a blank screen, and what matters is that it does NOT erase one** (`client/ui/screen.py`; `screen.fresh()` is the first statement of `main.main()`). Appended under whatever the terminal already held, the banner reads as a continuation of the previous run with the wordmark buried mid-screen — but that output belongs to the **shell**, so the reset **scrolls** (N newlines → `ESC[H` `ESC[J`) instead of erasing, leaving every prior line one flick of the wheel away. **`/clear` is the deliberate opposite** (`wipe()`, `ESC[3J` first): it discards the conversation, so leaving it scrollable above the prompt would be the bug — the two sequences live in one module precisely so that difference is stated once. Placed BEFORE the startup spinner (not in `show_welcome()`) so a warning from `client.start()` survives; that also covers `--resume` and the `/config`-`/model`-`/features` re-exec for free, since `os.execv` re-enters `main()`. `terminal_rows()` clamps the reported height (a 200-row cap, 24 fallback) so an absurd size can't mean thousands of blank lines, and the single write is TTY-gated + non-raising, so a pipe or CI log gets nothing.

**Four display rules in the same family:** a tool call's **name is colored** (`render_tool_call`, the file-op accent — in white it was indistinguishable from the model's prose); a multi-step task renders as a **checklist** (`render_step_list`: `[✓]` done, **green `[ ]`** executing, gray pending), windowed to 8 rows with counted elision so a long plan can't bury the answer, fed by `_run_subtasks_scheduled` from the single scheduling thread (`_run_subtask` runs on pool threads and would interleave) — **live in the pinned region, where the plan is ONE block whose own rows tick from `[ ]` to `[✓]`** (`turn_view.StepStatus`, a thread-safe sink shaped like `ReasoningStatus`; rendered by `tui`'s `steps_window`, wired as `agent.steps_sink` in `chat_interface._run_pinned_loop`), `stop()`ed in a `finally` so a cancel or a failed step hands the region back, and closed by ONE all-checked block printed to scrollback — the live block is transient, so that closing block is the plan's only permanent record. **A printed block is frozen the moment it lands**, which is why the older shape survives as the off-TTY fallback (`agent._print_step_list`/`_print_step_done`, scheduling-thread only, spinner stopped first): a block per WAVE — printed BEFORE its steps run — plus a `render_step_done` tick line per completion (`[✓] 2/3 <step>`, consumed via `as_completed` so it names the step that actually landed while the spinner label counts down, `_wave_label`; a LONE step isn't ticked, the next block marks it). Those appended lines are exactly what the live block replaced: in the common case — every subtask independent, hence ONE wave — the user watched five green `[ ]` rows stuck at `Steps 0/5` grow a separate `[✓] 1/5 …`, `[✓] 2/5 …` line per step instead of the rows in front of them getting checked; a resume prints a **marker line** (`render_session_notice` → `⟲ resumed <id>`), keeping the FULL id because `--resume <id>` matches by suffix; and a finished turn prints a **full stop** (`render_turn_end` → `· done in 7m22s · 11:08`, via `chat_interface._turn_end_line`) — a streamed answer just STOPS, so nothing separated "the model is finished" from "the next paragraph is still coming", and the spinner that meant _working_ lives in the toolbar, which is not scrollback and so can't answer the question a minute later. It is printed for **every** turn, fast ones included (a terminator you can only sometimes rely on terminates nothing) and the delivery-only turn a background sub-agent triggers, and it is timed at the PRINT rather than at `query()`'s return, because the post-answer learning steps still hold the prompt and are part of the wait; a cancelled turn is worded `⊘ stopped after 12s · 11:08` instead, which is also what resolves the transient `(cancelling…)`. **Nothing announces a restored compaction:** the old "N earlier messages carried as a summary" notice described an internal detail the user can't act on, above a transcript that had just replayed in full.

**UI-thread ↔ worker-thread invariants (a violation here HANGS the whole app):**

- **Never drop a `run_in_terminal` awaitable.** It suspends the app to write to scrollback and chains on `app._running_in_terminal_f`, so an un-awaited call both hides its own failure (it surfaces only as an unretrieved-task warning) and can stall a _later_ in-terminal write. Always `await` it inside a task with its own `except` — `_notice()` is the ready-made helper for a one-line dim message from the UI thread; the confirm echo in `_await_confirm` does the same and repaints in a `finally`.
- **A scrollback write must never gate a prompt.** The pinned confirm/approval prompt is painted by the app while the _worker_ blocks on an `Event`; if the echo can block the paint, the user gets a bare cursor with nothing to press.
- **Never block a worker thread on an unbounded `Event.wait()`.** Esc/Ctrl+C cannot reach a thread parked in `wait()`, so an unanswerable prompt becomes an unrecoverable freeze. Poll with a timeout and bail on `_cancel_requested()` (`_cancelled`, reset per turn). **A cancelled/failed wait must return the DENY answer, never the caller's `default`** — plan approval passes `default="approve"`, and a prompt nobody saw must never count as approval.
- **`run_dialog` is the deliberate exception:** its `done.set()` lives in a `finally` on the event loop, so it releases the worker even when the dialog raises. Don't add a timeout there — bailing out with `_pending_dialog` still armed leaves the app half-torn-down. Note `_open_detail` runs on the UI thread and so must NOT block on it (it pre-renders and stashes a `_pending_dialog` instead).
- **Thread affinity:** key handlers run on the event loop (so `loop.create_task` is fine there); anything called from the worker thread must marshal via `call_soon_threadsafe`. Check which thread a caller is on before picking one.

## Code Conventions

- **Comments** — concise and focused. One-line docstring per method; inline comments only for non-obvious "why", never restating the code. No verbose multi-line explanations or essays. Keep the surrounding file's comment density.
- **New features must reach EXISTING installs, not just fresh ones** — when a feature adds anything to the app home (`~/.mnemoai/`: a bundled skill, an `*.example`, a `prompts.yaml` key, a new config file, seeded data), it MUST be delivered so a user who **already installed the app** gets it on the next upgrade — never gated on a first-run-only / empty-dir condition. Use the `seed_example_files()` **per-item "seed if absent"** pattern (each bundled item copied when its own destination doesn't exist), not "seed only when the whole dir is empty". To push an **update to an already-seeded item**, refresh it too — but only when safe: `*.example` reference files (never loaded as config) are refreshed whenever they differ (`_refresh_example`); a bundled skill's `SKILL.md`, a bundled slash command AND the live `prompts.yaml` are refreshed in place only when the installed copy is **pristine** (hash in `_PRISTINE_BUNDLED_SKILL_HASHES` / `_PRISTINE_BUNDLED_PROMPTS_HASHES` / `_PRISTINE_BUNDLED_COMMAND_HASHES` — a version we shipped, unmodified; `_refresh_pristine_skill` / `_refresh_pristine_prompts` / `_refresh_pristine_command`, all over one `_refresh_if_pristine`), never over a user's edits — this is how a change to an EXISTING prompt key reaches installed users (the bundled-fallback loader only fills MISSING keys). Prefer **presence-based / code-driven** activation over a new config toggle so nothing depends on the user editing a pre-existing `config.yaml` (e.g. STEERING.md: the file's presence is the switch; new `config.yaml`/`prompts.yaml` keys fall back to a bundled default in code — the live `config.yaml` is never rewritten). Always add a test that the item reaches an **already-populated** app home (see `tests/unit/test_paths.py::test_seed_skills_per_skill_reaches_populated_dir` and `test_pristine_installed_skill_is_refreshed`), and never clobber a user's own edits.
- **Tests** — pytest unit suite in `tests/` covers pure-logic modules (no LLM/Ollama needed). Run with `python -m pytest`. See the Testing section below
- **Error handling in tools** — `@tool_error_handler` decorator (`server/error_handler.py`) for standardized responses
- **Action confirmation** — destructive tools (`execute_bash`; `fs_write`/`file_edit`; `memory` writes) are hard-gated by `LangGraphAgent._confirm_tool()` in BOTH `_execute_tools` and `_run_worker_loop`, before `tool.invoke()`. It must live client-side: the MCP server is a piped subprocess and can't prompt the terminal. Toggles `REQUIRE_BASH_CONFIRMATION` / `REQUIRE_WRITE_CONFIRMATION` (default true), `REQUIRE_MEMORY_CONFIRMATION` (default false); non-TTY auto-proceeds. **A second, POST-call gate** (`confirm_result`, category `git`, toggle `REQUIRE_GIT_CONFIRMATION` default true) resolves a tool that refused with `requires_confirmation` — and `allow_dangerous=True` is confirmed BEFORE the call, tool-agnostically, so the model can't wave through a refusal it was just given. The prompt is `Proceed? (y/N/a)` — `a` trusts that whole category (`bash`/`write`/`memory`, tracked in `_trusted_confirm_categories`) for the rest of the session so a multi-step task doesn't re-prompt; default-deny otherwise. **This client gate is a confirmation layer, not the last line of defense**: a separate server-side floor (`server/tools/safety/`, above) hard-blocks catastrophic commands and system-path writes regardless of confirmation, since the MCP server can be driven directly
- **Auto-approve mode (`/auto`)** (`client/agent/auto_approve.py`) — a session-scoped tier that answers the confirm prompt instead of the user: `off` → `edits` (writes inside the CWD) → `writes` (any path + `memory`) → `all` (+ `bash`), cycled by bare `/auto` or set by `/auto <tier>`, badged on the input line. Same flag pattern as plan mode (`client.auto_approve_mode` → `auto_approve_provider` → the agent), read at ONE rung of `confirmation_gate._gated_prompt` — after the toggle and the `a`-trust check, before the headless branch. **It is a session TRUST, not a new permission:** the safety floor, the plan-mode block and a hook's `deny` are all decided in `tool_loop.run_tool_calls` before the gate, so no tier can widen them; `/plan` resets the tier (read-only and don't-ask can't both hold). The `git` category is auto-approved by NO tier (`NEVER_AUTO`) — that gate exists to keep the model from waving through its own `requires_confirmation` refusal. `edits` scoping (`_within_workspace`) resolves symlinks on both sides and compares on a separator boundary (`/repo-old` is not inside `/repo`); an unresolvable target is outside, since the prompt is the safe answer whenever scope is unknown. The module is pure (mode + args in, bool out), so the ladder is unit-testable and the gate keeps one decision point
- **Plan mode (enforced, user-toggled)** — `/plan` flips `client.plan_mode_active`; the agent reads it via `plan_mode_provider` and `_is_blocked_by_plan_mode` HARD-BLOCKS the mutating/exec tools (`_PLAN_BLOCKED_TOOLS` = execute*bash, fs_write, file_edit, git_safe, git_commit_safe, start_background_task) at both chokepoints, **above** `_confirm_tool` (blocked → never even prompts). Conditionally allowed: `execute_bash` when read-only (`_is_readonly_bash`), and `fs_write`/`file_edit` only for the plan file (`.md` under `plans_dir()`, `_is_plan_file`). Read-only tools + `memory` always pass. `client.query()` prepends a read-only reminder each turn (`_plan_mode_reminder`). **Approval → execute handoff:** the model calls `exit_plan_mode(plan)` (thin stub in `_ALWAYS_AVAILABLE_TOOLS`); `_handle_exit_plan_mode` intercepts client-side at both chokepoints, drives `_plan_approval_ui` (y=approve&run / e=edit in `$EDITOR` / n=keep planning), then `client._approve_plan` flips plan mode off, persists to `plans/plan*<ts>.md`, and hands the plan back so the model executes **in the same turn** (non-TTY auto-approves). `exit_plan_mode(plan, allowed_bash=[…])`pre-declares commands stored on`agent.\_preapproved_bash`so`\_confirm_tool`auto-confirms them (equal/prefix match,`\_is_preapproved_bash`). Approval also sets `agent.\_execute_plan_route = True`so`\_effective_route`forces the **full** toolset for the rest of the task (else a read-only re-classification would leave the write tools unbound);`\_route_after_classify`sends those turns straight to the agent, not the orchestrator. Pre-approved bash + route pin are plan-scoped (cleared on`/clear` and plan re-entry). This enforced path is the only plan mode (the legacy JSON-workflow tools were retired)
- **Async/sync bridge** — MCP client uses a background thread with `asyncio.new_event_loop()` in `client/mcp_tool_wrapper.py`; sync callers use `run_coroutine_threadsafe`
- **Imports** — absolute (`from mnemoai.…`), at module top level, grouped stdlib → third-party → first-party and **alphabetized within each group** (enforced by `ruff check --select I .`, the CI gate). **Lazy/function-local imports are the exception, NOT the default** — add one only for a real circular import or a heavy/optional dependency you must defer; convenience/habit are not reasons. **Prove the cycle before going lazy:** cold-import the module that would close the loop with the import at the top (e.g. `PYTHONPATH=src python -c "import mnemoai.client.agent.agent"`, and worst case the new module first); if both resolve, keep it at the top. A cycle needs A→B _and_ B→A both at top level; a lazy back-reference makes a top-level forward import safe. **Test-isolation consequence:** a top-level `from x import name` binds `name` into the importing module, so patch it where it's _looked up_ (`monkeypatch.setattr(subagents, "agents_dir", …)`), NOT at its source — the latter silently no-ops.
- **Type hints** — used for LangChain/LangGraph state schemas (`TypedDict`), model classes; not enforced everywhere
- **Naming** — snake_case functions/variables, PascalCase classes, UPPER_CASE config keys
- **File I/O** — JSON for persistence (playbook, todos, profile, episodic metadata), SQLite for chunk cache
- **Token counting** — tiktoken for OpenAI/Bedrock, character-based approximation (÷4) for Ollama

- Layout: `tests/unit/` (pure-logic) and `tests/integration/` (live agent). Configured via `pytest.ini` (testpaths=tests). `tests/conftest.py` puts the repo's `src/` dir on `sys.path` so `import mnemoai` resolves from a checkout with no install step.
- **Unit tier (default):** deterministic, pure-logic tests — no LLM, Ollama, or network needed, runs in seconds. Covers `utils/bm25.py`, `client/agent/reasoning_utils.py`, `utils/formatting/` (response_parser, url_formatter, code_formatter), `client/agent/orchestrator.parse_subtasks`, `server/error_handler.py`, `server/tools/git_safety.py` (command-danger classification), `server/tools/file_edit.py` + `glob_search`, `execute_bash` timeout/process-group behavior + output cap, `grep_search` modes/total-cap/context/non-UTF-8/regex-error, the `read_state` read-before-write gate, background-task group-cancel, `file_encoding` BOM/CRLF round-trips + encoding-preserving edits, streamed line reads, skill token-budget/memoization/argument-substitution, `client/memory/episodic_memory` heuristics, Bedrock/Mantle model wiring (`test_bedrock_endpoint.py`), vision content normalization (`test_vision_content.py`), and conversation compaction incl. token-aware retention, parallel map-reduce summarization, eviction-first, and the ground-truth trigger + reasoning-disabled summary model (`test_conversation_compaction.py`, `test_preflight_compaction.py`), user tool hooks incl. loader tolerance, deny-beats-allow, non-blocking timeout and the startup snapshot (`test_hooks.py`, plus the gate-order cases in `test_tool_chokepoints.py`), the `/doctor` checks (`test_doctor.py`), session naming (`test_session_labels.py`), the pinned footer — layout/meter/thresholds (`test_status_bar.py`) plus the one-place-only context readout (`test_status_footer.py`), the multi-step checklist — rows ticking in place in the pinned region vs the printed per-wave fallback (`test_step_checklist.py`), and the three workspace reports — the touch ledger incl. spelling collapse and thread safety (`test_file_ledger.py`), `/diff` numstat/rename parsing + a real throwaway repo + the guard that no git verb can mutate (`test_diff_report.py`), and `/copy`'s extraction + transport order incl. SSH-puts-the-terminal-first (`test_clipboard.py`), and `/rewind` — the turn boundary under every injection, the compaction refusal, the two record shapes and the withdrawal surviving a resume (`test_rewind.py`, plus the pinned-state picker cases in `test_session_log.py`), auto-approve — the tier ladder, workspace scoping, and that no tier reaches past the gates above it (`test_auto_approve.py`), and per-area models — tolerant config parsing, a variant re-snapshotting every param (incl. a `TYPE` override), the None-on-failure fallback and the `/params` re-derive (`test_area_models.py`).
- **A test must never run the developer's own tool hooks.** `tests/conftest.py::_no_user_hooks` (autouse, whole suite) pins an empty hooks snapshot: hooks are shell commands read from the real app home and every tool call fires them, so without it a machine with a `hooks.json` would have its own rules executed — and possibly deny — the suite's tool calls. `test_hooks.py` resets the snapshot and supplies its own registries.
- Unit tests must not require a `config.yaml` — modules degrade gracefully without one. Keep import-time side effects config-independent so new code stays unit-testable.
- **Integration tier (`tests/integration/`, marked `@pytest.mark.integration`):** drives the real `LangGraphClient` + Ollama + MCP subprocess (greeting/routing, tool calls, bash timeout, no-silent-empty-turn). Auto-skipped unless a runtime `config.yaml` exists AND the configured Ollama host is reachable (see `tests/integration/conftest.py`). The shared client is session-scoped; an autouse fixture calls `clear_context()` between tests for isolation. **A session-scoped fixture redirects `$MNEMOAI_HOME` to a tmp dir** (pinning `$MNEMOAI_CONFIG`/`$MNEMOAI_PROMPTS` to the already-resolved real files so the tier still runs against the configured provider): because this tier drives a REAL client, every side effect on the app home is real — without the redirect each run wrote session transcripts into the developer's own `~/.mnemoai` (surfacing in `--resume` as fake conversations of test prompts) plus episodic/playbook entries learned from test queries. Any new test that constructs a real client must keep that isolation.

## Adding a New MCP Tool

1. Create `server/tools/my_tool.py`
2. Define function with `@mcp.tool()` decorator (receives `mcp` from registration). **Write it as a plain `def` unless the body really `await`s something** — a blocking `async def` runs inline on the server's single event loop and stalls every other agent's tool call (see the thread-offload pattern); a sync tool is offloaded to a thread automatically at registration
3. Add `@tool_error_handler` for standardized error responses
4. Register in `server/tools/tools_manager.py` → `register_tools()` method
5. If conditionally enabled, gate behind a config toggle
6. Add route mapping in `client/agent/router.py` → `ROUTE_TOOLS` if it belongs to a specific category

## Adding a New LLM Provider

1. Add provider case in `models/controllers/llm_controller.py` → `initialize_model()`
2. Register the provider's supported config keys in `models/provider_params.py` (the registry consumed via `build_kwargs` and used by `/model` pruning)
3. If custom LangChain model needed, create class in `models/chat_models/`
4. Add embedding support in `models/controllers/embeddings_controller.py` if provider offers embeddings
5. Add vision support in `models/controllers/vision_model_controller.py` if applicable
6. Document config structure in all `utils/config.yaml*.example` templates

## Stability & Versioning

Semver. The **public contract** (what a major bump protects) is: `config.yaml` keys (model sections, `ENABLE_*`/`REQUIRE_*` toggles, documented sections), the `mcp.json` `mcpServers` schema, the `hooks.json` schema (event names, `matcher`/`type`/`command`/`timeout`, the exit-code + stdout-JSON contract), the CLI slash-commands + `mnemoai` console command (incl. its `--no-verbose`/`--auto`/`--resume`/`--continue` flags), and the `mnemoai-assistant` dist / `mnemoai` import name. Everything under `client/`/`server/`/`models/`/`utils/` not in that list is internal and may change freely. All changes go in `CHANGELOG.md`; releases follow the checklist in `docs/development/index.md`. CI (`.github/workflows/tests.yml`) runs the unit tier + import-sort on push/PR; the integration tier is run locally before releases.

## Known Limitations

- Unit tests cover pure logic only — agent/LLM integration paths still need manual verification (run the integration tier + the release checklist before releasing)
- MCP server is a subprocess — debugging requires attaching to child process or reading logs
- No Docker/containerization — runs directly on host with system Python/conda/venv
- No database — all persistence is file-based (JSON, FAISS index files, SQLite chunk cache)
- Single-user — profile name in config isolates data but no auth/multi-tenancy
- `ripgrep` (rg) required for `grep_search` tool — install separately
